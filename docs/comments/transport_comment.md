## 重试预算常量（RETRY_ATTEMPTS / RETRY_BACKOFF / RETRY_AFTER_CAP）

- 传输失败自动重试预算：只重试**首个流条目之前**的瞬态失败（请求没送达、服务端明确说稍后再来、连接初建即断）。连接阶段与首个流条目之前两个阶段共用同一份预算——前一阶段耗尽，后一阶段不再重试。
- 无 `Retry-After` 指引时的固定退避。
- `Retry-After` 指引的等待上限：更长的等待不自动进行——失败卡交还用户，重试按钮在手（状态机对网络/限流错误的既有出口）。

## IDLE_TIMEOUT

- 流式空闲超时：连续这么久没有任何字节到达即判传输停摆，流以 `GlossError::EngineNetwork` 终结（首个 `Err` 终结流的端口契约不变）。取值从宽以覆盖首字节等待——推理类模型出首个字节可以远慢于普通请求——也覆盖流中途的服务端生成间歇；只惩罚「连接还在、字节不来」的静默悬死，对长回复没有总超时那样的合法误杀。

## read_bounded_body

- 读响应体但不超过 `limit` 字节（丢失的只是诊断文本，不是业务数据）。读取中断不当作「正常读完」静默截断：留一条 debug，错误体按已读部分交给诊断解析（半截 JSON 会退化成「只报状态码」）。

## Resolved

- 一次请求的解析产物：端点、密钥与 wire 请求体。请求体在构造处一次性序列化成 `Bytes`（图像任务的 base64 可达 MB 级，`.json(&Value)` 会在每次尝试时整体重序列化一份临时缓冲）；`Bytes` 克隆只递引用计数，重试复用零拷贝。
- `Resolved::build`：组装并序列化请求体。序列化失败只可能是本地构造出非对象形态的 `Value`（请求体构造恒产出 JSON 对象），按请求异常上抛。

## TransportFail

- 一次传输尝试的失败载荷：错误分类 + 服务端的稍后重试指引（`Retry-After` 头的秒数形态）。指引不进 `GlossError`——它是传输层重试的内部量，出了这层就是普通失败。

## retry_delay

- 传输失败是否值得自动重试及等待时长（纯函数）：预算未尽且错误是瞬态（网络/限流）才重试；等待取 `Retry-After` 指引与上限的较小值，无指引用固定退避。鉴权、参数与环境类拒绝重发无益，与预算耗尽同返回 None。

## parse_retry_after

- `Retry-After` 头的秒数形态解析（HTTP 日期形态返回 None，回落固定退避）。

## idle_deadline

- 空闲看门狗的到点时刻（纯函数）：`Sleep` 的初装与复位都用它给定时刻。

## send_once

- 发起一次传输尝试：端点、密钥与请求体已就绪（解析产物），发请求、查状态、包 SSE 流。失败以 `TransportFail` 上交（状态失败随附 `Retry-After` 指引）；重试判定归 `connect_with_retry` 与 `FirstByteStream`。
- 请求体已在 `Resolved::build` 序列化成字节，这里只补 JSON 的 content-type（`.json` 的另一半职责），克隆只是递引用计数。
- 服务端诊断文本（可能是 JSON 错误对象）：只取 message 字段，不转述整个响应体；密钥在请求头里，不会出现在这里。读取带上限——错误网关/WAF 可能回几百 MB 的劫持页，不能整份吃进内存。

## connect_with_retry

- 连接阶段的重试循环：逐次尝试，瞬态失败在预算内退避后重试，其余失败与预算耗尽原样上抛。预算余额随成功返回——首个流条目之前的重试（`FirstByteStream`）接着用同一份预算。

## FirstByteStream

- 首个流条目之前的重试包装：内建流在产出**任何**条目之前的 `Err`，若是瞬态失败且预算未尽，丢弃空流、退避后重新发起请求（消费方无感）——此刻没有任何增量交付过，不存在半截产物要保。首个条目一旦交付（增量或终结条目），错误一律原样放行：中途断流多半是确定性故障，重头重播还会让已渲染的流式正文错乱。`attempt` 与连接阶段同形状，共用同一份 `RETRY_ATTEMPTS` 预算；重连只此一次、失败原样上交，不链式重判——现行预算下重连发出时余额必为 0，这一箭也是对失败端点的重试上限。
- 字段 `connecting`：进行中的重连（退避 + 重新请求）；在位时 `inner` 必为 None。
- `poll_reconnect`：推进进行中的重连——`None` = 新流已装上，回主循环继续；`Some` = 挂起或以错误终结。

## SseStream

- 把响应的字节流适配成 `TaskStream`：SSE 逐行解码，吐文本增量，`[DONE]` 上交一条携带结束原因的终结条目（`TaskChunk::Done`）。
- 手动实现 `poll_next`（与编排层的手工轮询同一风格），不引 futures-util：状态机只有「攒够一行 → 产出条目 → 继续拉字节」三步。首个 `Err` 即终结流（端口契约），此后不再拉取字节。
- 字段 `produced`：是否产出过增量——零增量的「成功」是坏响应（网关忽略 `stream:true` 返回非流式 JSON、劫持页返回 200 HTML、模型只回 refusal 等），不能当成功产物写进缓存——用户会看到空白卡片，重复触发还命同一份空白。
- 字段 `idle`：空闲看门狗，每次收到字节即复位；到点未复位说明连接悬死（连着但不来字节），轮询以 `GlossError::EngineNetwork` 终结流。

## SseStream::absorb

- 收下解码器产出：增量入队，`Done` / `Failed` 终直流。
- 终结之后再无契约地位的字节（解码器对 [DONE] 后的输入同样沉默）。
- 零增量的「成功」是坏响应，即便服务端声明了正常结束。

## SseStream::finish_without_error

- 连接关闭的收尾（服务端没给 `[DONE]`）：一条增量都没产出过就是坏响应；产出过则按流自然耗尽收场（结束原因未知，不产出 Done）。`ready` 先于 `finished` 被排空，所以这条 Err 一定排在已入队的增量之后。

## SseStream::poll_next（Stream impl）

- 看门狗先于内层轮询：连接悬死时内层恒 Pending，唯一能终结流的就是它。已入队的增量先交付（末次字节到达时看门狗已复位，能走到这说明静默期确实过满了）。
- 连接断了：把错误排在已收下的增量之后（端口契约是「首个 Err 终结流」，之前到达的增量仍应交付）。
- 连接关闭即流结束：服务端没给 [DONE] 也按正常收尾，顺便收下尾巴里那条完整但没换行终止的增量。
