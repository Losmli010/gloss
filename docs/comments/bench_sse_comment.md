## 缘由与落位

- 2026-11-20（方案 D7 前半）流式事件解码全仓无任何量化数字，是三类量化空白之一（C7 量化的前置）；解码器随传输分包落位住开放接口（OpenAI）方言，基准按依赖同位落在本包。
- 2026-11-20 解码器是库内私有实现（pub(crate)），基准目标（benches 目录，独立 crate）够不到——基准源文件以路径属性把生产源文件单源并入，与测试桩的跨包同源机制同款；零公共面改动，测到的与线上跑的是同一份源码。

## 用例设计（四档）

- 2026-11-20 stream/one_push：整流一次喂入，最优路径——行扫描、多字节字符与 JSON 解析同批完成。
- 2026-11-20 stream/chunk_64b：定长 64 字节分块喂入，贴近传输协议（HTTP）分块的真实粒度，量化跨块待缓冲拼接的成本。
- 2026-11-20 stream/chunk_1b：逐字节喂入，最坏路径——待缓冲区每字节全扫一次，块界正确性与多字节字符完整性在这里量化上界。
- 2026-11-20 line/limit_breach：单行越界（超过行长上限一字节），量化行长上限的守卫路径——分配、拷贝与扫描都在守卫前发生。

## 无 panic 写法（clippy 纪律）

- 2026-11-20 bench 目标 harness = false，不在 clippy.toml 的 test 豁免范围（allow-*-in-tests 只认 #[test] / #[cfg(test)]），unwrap / expect / panic / print 与生产同罪。流文本与越界字节序列全部字符串拼接 / 字面量构造（不经 serde 解析、不打印），解码器有状态随测量新建（无法外提），产出事件表交给 black_box。

## 并入模块的 dead_code 豁免

- 2026-11-20 基准目标编译时 cfg(test) 仍然打开，被并入源文件的测试模块照常参与编译，而基准目标无测试收集器，测试模块里只剩从未被调用的助手函数——死代码判罚落在并入声明上（`#[allow(dead_code)]`），只压掉本次基准编译，生产库的正常编译（测试经收集器调用、无死代码）不受影响；生产源文件本身零改动。

## 基线（2026-11-20，C7 量化前置的首跑）

- 2026-11-20 运行环境：Intel Core i5-7360U @ 2.30GHz（x86_64）/ darwin 22.6.0 / rustc 1.96.1；criterion 默认采样。中位数（流夹具 128 事件约 9.5KB，越界序列 1MiB 加一字节）：
  - stream/one_push 110.9µs、stream/chunk_64b 119.1µs、stream/chunk_1b 358.0µs、line/limit_breach 727.1µs。
- 2026-11-20 数字形态：整流与定长分块同量级（跨块待缓冲拼接在 64 字节粒度上增量约 7%），逐字节呈约三倍开销（待缓冲区逐字节全扫的最坏形态），行限守卫路径由整段分配加扫描主导。
