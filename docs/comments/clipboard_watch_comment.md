## ClipboardWatchSource（剪贴板图片哨兵源，2026-10-10，方案 §5.2）

- **为什么只读 changeCount + types**：读内容会触发 macOS 15+ 的“允许粘贴”
  授权流程（用户未授权时每次复制都弹系统框），而 changeCount 是 NSPasteboard
  的纯元数据 ivar、types 是 flavor 名单，两者都不触碰内容、不触发授权。
  哨兵高频运行的代价因此可以压到可忽略；“要不要读内容”的授权时刻被推迟
  到用户真的复制了图片之后的取材命令②（一次性、可拒绝、拒绝后有失败路径）。
- **为什么选 NSPasteboard.changeCount 而不是复用 Carbon `PasteboardSynchronize`
  （`ffi::pasteboard` 的 K_PASTEBOARD_MODIFIED 路线，剪贴板兜底读取在用）**：
  Synchronize 的 modified 标志是**消费式**的——读一次就清零，只能闩锁成 0/1
  （`ChangeMonitor` 那样），无法区分“启动以来第几次变化”；多张图连续复制、
  开关热切换重记基线这些场景都需要单调计数。NSPasteboard 的 changeCount 是
  持久单调整数，天然匹配“基线 + 前进”的哨兵语义。代价是多开一条
  objc2-app-kit 依赖面（NSPasteboard feature），换掉的是整个闩锁状态机。
- **为什么基线记在构造时（`new` → `rebaseline`），而未武装路径允许首轮
  poll 懒记**：构造时机在组装段（主线程，事件线程尚未启动），此时读到的
  就是“启动时的既有剪贴板”，满足“启动内容不触发”；构造期查询失败
  （理论上 generalPasteboard 不会失败，但防御）不阻断启动，留未武装态由
  首轮 poll 懒记——两种路径共享同一段“记基线、不触发”的逻辑。
- **为什么开关关时把 `seen` 置回 None**：若保留旧基线，用户关掉开关期间
  复制的图片会在重新打开的第一次 poll 触发——“打开设置页开关就弹一张
  几小时前的旧图卡”违背预期。置 None 使重开时重记基线，重开时刻的剪贴板
  内容不触发，与启动语义同构。代价是关→开会丢掉关闭期间的所有变化——
  这是刻意的：哨兵是“观察新图”而非“补办历史”。
- **为什么节流的是查询而不是事件（`next_query` 闸门在 count() 之前）**：
  changeCount 查询虽廉价，但事件线程每 33ms tick 都读一次系统 API 没有必要；
  250ms 的观察延迟相对“复制 → 读图 → LLM 首字”的秒级端到端不可感知。
  节流闸门放在未武装检查之后、查询之前——武装轮不受节流影响。
- **为什么前进即消费基线（`seen = Some(current)` 在 types 复查之前）**：
  纯文本复制若不消费基线，每 250ms 都会对同一个未变化的 changeCount 反复
  查询 types；消费后同一次变化只查一次 types。图像变化同理——一次变化至多
  发一个①，重复轮询不会重复触发任务（重复触发的下游防线在 App 侧探测互斥，
  不在哨兵）。
- **为什么 `PasteboardObserver` 用 `Arc<AtomicU64>` 而不是让①携带载荷**：
  ① `PasteboardImageObserved` 无载荷是方案定死的协议（channel.rs 步骤 3 已
  合入），观察时刻的 changeCount 只能旁路共享。哨兵与读取器都在事件线程
  运行（同线程顺序消费），原子量只为跨闭包共享（两个 Box<dyn EventSource>/
  FnMut 各自持有一份），无真实并发。初始值 0 与任何真实 changeCount 不匹配
  的设计使“未经哨兵的取材命令”天然按竞态丢弃——比加一个“有无记录”状态
  少一个状态位，语义等价。

## `pasteboard_has_image`（图像类型判定）

- **为什么认 TIFF + PNG 两种 flavor**：⌘⇧4+Ctrl 截图与多数 macOS 应用
  “复制图像”写的是 public.tiff；浏览器/文件管理器复制常写 public.png。
  只认其一会漏掉半边来源。其它图像 flavor（如 JPEG 的 public.jpeg）暂不
  认——arboard 的 macOS 读取栈走 TIFF/PNG flavor，认了也读不出。
- **为什么用 extern static 而不是手写 "public.png" 字面量**：AppKit 常量
  与系统实现同源，`unsafe` 面只有一次 extern static 读取；手写字符串省掉
  unsafe 但引入“常量改名即静默失效”的漂移面。常量是 NS_TYPED_EXTENSIBLE_ENUM
  的稳定契约，风险不对称地偏向用系统常量。

## `WatchRoundFlag`（取材轮次抑制，2026-10-12；闩锁化 2026-10-14）

- **为什么哨兵要被取材轮次抑制**：文本兜底取材（selection/clipboard.rs）会
  两次写系统剪贴板——目标应用响应注入的复制写入选区文本、轮次末按快照
  恢复原内容。这两次变化都会推进 changeCount，恢复写回的内容若含图像
  （用户之前复制过图片），哨兵会把它观察成一次“新复制”并产出①：在途
  的划词探测被粘贴板探测顶掉（探测互斥），新鲜取到的选区文本按陈旧丢弃，
  旧图被再触发成一次图片任务。实测日志（2026-10-12，gen14→gen15、
  gen16→gen17）证实了这条“划词被自己的恢复写回吃掉”的回路，是“图片
  解释后再划词不弹窗”的直接根源。抑制采用“轮次内作废基线”而不是
  “忽略具体某次计数”：轮次内有两到三次变化（目标写入 + 恢复写回）且
  精确归属无法从 changeCount 分辨，作废基线把轮次窗口内的变化整体吞掉，
  复用开关关→开的重记基线语义，不新增状态位。代价是轮次窗口内（亚秒级）
  用户真实的新复制不触发——该窗口本就处于活跃取材中，与既有的①②竞态
  丢弃语义同向。
- **为什么是“置位后存活到下一次查询”的闩锁而不是 RAII 守卫（2026-10-14，
  替换首版守卫实现）**：首版 `enter()` 返回守卫、drop 即解除，隐含假设是
  “查询会落在轮次中间”——实际不成立。轮次跑在事件线程的命令处理器里，
  而哨兵查询在 `tick` 的命令循环之后执行，处理器阻塞 run loop 期间定时器
  不重入：生产路径上任何查询都在守卫 drop 之后，`is_active()` 恒为 false，
  抑制整段失效，“图片解释后再划词恒回显上一次解释（缓存命中）”在守卫
  版本下依旧复现。闩锁把抑制的存活期从“置位方作用域”改成“到下一次
  查询为止”：命令处理器置位，同一 tick 紧随的查询消费它并作废基线，
  轮次内全部变化照旧被吞。守卫随之删除——闩锁的寿命由查询节奏收口，
  panic 展开与取材失败都不再需要 RAII 兜底（消费只取决于下一次查询，
  与置位方的存亡无关）。
- **为什么开关位共享而不走通道**：哨兵源与文本取材处理器都在事件线程上
  顺序运行（tick 先消费②命令再轮询事件源），轮次置位与哨兵查询天然无
  交错，`Arc<AtomicBool>` 只为跨两个闭包共享句柄，与 `PasteboardObserver`
  同一取向。

## WatchRoundFlag / poll_at 闩锁消费（2026-10-15，计数归因）

- **为什么从“盲吞”改成“计数归因”**：原设计把“置位后到下一次查询”的
  全部 changeCount 前进都当作本应用写盘吞掉。真实场景里截图工具的拖拽
  既触发划词探测、又把用户复制的图片写进剪贴板——该图片恰好落在探测轮次
  窗口内，被当作恢复写回误吞，用户感知“复制图片不出卡”（连续复现）。
- **为什么用计数而不是内容指纹**：备选方案是在哨兵武装基线时读一份内容
  指纹、闩锁消费时对比。否决——哨兵读内容会触发 macOS 15+“允许粘贴”
  授权（模块红线：哨兵只读 changeCount + types 元数据），且把授权时刻
  提前到启动期。计数归因只用三次 changeCount 元数据读数（基线、轮次前、
  消费时），零授权影响。
- **归因口径**：闩锁携带（轮次前计数 pre，自报写盘数 ours）；消费时
  `current − 哨兵基线 > ours` 即存在外来写入 → 保留基线、照常走前进
  判定（是图即触发）；否则全部变化可归因自身 → 吞掉并就地重记基线。
  ours 只计“确定发生”的写盘：已确认的注入复制 + 已执行的恢复写回
  （失败轮不恢复，见 selection_clipboard 记录），宁可少计（可能多触发
  一次由 has_image 兜住）不可多计（会把用户复制吞掉）。
- **为什么消费时不再作废基线**：原实现吞掉后 seen=None，下一轮才重记；
  新实现消费时直接读到现值、就地重记（省一轮查询，也消除“重记前的
  外来前进被误吞”的窗口）。读数失败仍走保守路径：作废基线重记。
- **置位点移进兜底读取器**：置位需要“本轮自报写盘数”，只有兜底读取
  器知道（确认与恢复都发生在它内部）；AX 成功、权限缺失、激活成功等
  不写盘的轮次从此不再置位闩锁——它们的窗口内外来复制天然放行。

## WatchRoundFlag::enter 合并置位（2026-10-15，评审补）

- **为什么合并而不是覆盖**：划词探测无在途去重，连续两个手势的兜底轮次
  可以先后写盘、共用一次闩锁消费。覆盖会让后一轮的 pre 抹掉前一轮的
  写盘记录：基线到现值的变化数超出合并后的自报写盘数，前一轮的自身
  写盘被误判为外来——恢复写回的旧图恰好因此复活（回归）。合并口径：
  pre 取更早者、ours 累加，两轮写盘都得到归属；外来余量照常放行。
- **已知限界（接受）**：ours 的“一次确认复制 = 一次 changeCount 前进”
  假设在个别应用（一次复制多次前进）下会低估 ours → 误判外来 → 可能
  陈旧复活一次。常规应用一次复制恰一次前进、恢复恰一次（Clear 一次，
  Put 不前进），成立面广；要消除需读内容归因，触碰“允许粘贴”授权
  红线，不值得。哨兵按外来放行后还有 has_image 与观察竞态两道闸，误
  触发面有限。
- **Mutex 中毒**：锁内无用户代码，结构上不可达；一旦发生以
  `into_inner` 取回内值继续（`Option<RoundWrites>` 无需毒化防护），
  失败面为零，符合“降级有痕迹”的取径——此处选择“无失败路径”而非
  “失败留痕”。

## 符号契约（自代码注释迁入）

- `POLL_INTERVAL`：哨兵的自节流节奏：观察延迟远低于复制到弹卡的端到端预期，节流省下的是事件线程每轮 tick 的查询。
- `PasteboardImageObserved`：哨兵本轮的观察产物：剪贴板出现了新图片（无载荷——内容在取材命令②再读）。组装点把它映射为 `PlatformEvent::PasteboardImageObserved`。
- `PasteboardObserver`：① 发出时刻的 changeCount 观察记录：哨兵写入、取材读取器比对——②到达时现值与记录不一致即剪贴板在①②之间被覆盖（竞态），取材静默丢弃。两侧同在事件线程上运行，原子量只为跨闭包共享；初始值 0（changeCount 恒非负）与任何真实读数不匹配，未经哨兵的取材一律按竞态丢弃。
  - `record`：记一次①观察：同 crate 内测试也用它播种观察记录（`ClipboardImageReader` 的注入单测），与生产哨兵同一条写入路径。
  - `matches`：② 取材时刻的现值是否仍是①观察记录的那次变化。
- `RoundWrites`：一轮取材自身写盘的计数归因：`pre` 是写盘前读到的 changeCount，`ours` 是本轮确定由自身引起的写盘次数（已确认的注入复制 + 已执行的恢复写回）。哨兵消费闩锁时，超出 `pre` 的变化里减去 `ours` 还有剩余，即存在本轮之外的外来写入（用户的真实复制），照常触发。
- `WatchRoundFlag`：取材轮次的哨兵抑制闩锁：文本兜底取材（注入复制 → 确认 → 恢复）会写系统剪贴板，这些变化是本应用的副产物，不得产出观察事件——否则恢复写回的旧图会再触发成一次图片任务。但轮次窗口内也可能落进用户的真实复制（截图工具的拖拽既触发划词探测、又把图片写进剪贴板），不能盲吞：闩锁携带本轮写盘的计数归因（`RoundWrites`），消费时把超出哨兵基线的变化数与自报写盘数相减——有剩余即外来写入，照常走前进判定。轮次（命令处理器）与哨兵查询同在事件线程顺序运行，且事件源只在命令全部抽干后轮询——查询永远不会落在轮次中间，闩锁因此设计成置位后存活到下一次查询，由查询消费（`take`）。置位与消费两侧各持一份句柄同在事件线程运行，锁只为跨闭包共享、无争用。
  - `enter`：进入取材轮次：记录本轮写盘的计数归因，由下一次哨兵查询消费（见类型注释）。无需守卫收口——闩锁的寿命到下一次查询为止，不随置位方的作用域结束。前一轮尚未被消费时合并归因（起点取更早的计数、写盘数累加）：连续两轮写盘后一次消费，两轮的自身写盘都得到归属，不会把后一轮的写盘误判成外来复制。
  - `take`：消费闩锁：置位过即取出计数归因（返回 `Some`），闩锁同时复位。
  - `peek`：读取当前挂起的计数归因（同 crate 测试观察口），不消费。
- `ClipboardWatchSource`：剪贴板图片哨兵源：事件线程每轮 tick 抽干一次（`EventSource::poll`），源内按 `POLL_INTERVAL` 节流查询；开关关时只读共享位、不碰系统 API。
  - `enabled` 字段：触发开关（配置快照初始化、设置页热切换）；关态不查询。
  - `observer` 字段：① 发出时刻的 changeCount 观察记录，供②比对竞态。
  - `round` 字段：取材轮次抑制闩锁（见 `WatchRoundFlag`）：句柄经 `round_flag` 交给文本取材处理器置位，查询消费。
  - `seen` 字段：已记基线的 changeCount；`None` = 未武装（构造时读不到、开关刚重开或取材轮次刚结束），下一轮到查询只记基线、不触发。
  - `next_query` 字段：下一次允许查询 changeCount 的时刻（节流闸门）。
  - `interval` 字段：查询节奏（注入测试驱动时序断言）。
  - `new`：生产构造：构造时读一次 changeCount 记基线（启动时的既有剪贴板内容不触发）；读不到保持未武装，首轮 poll 懒记。开关位按启动配置快照初始化，运行中由设置页置位热切换。
  - `observer` / `round_flag`：① 观察记录与闩锁的共享句柄：交给同一次装配的 `ClipboardImageReader`（② 取材时比对现值判定竞态）与文本取材处理器（置位闩锁）。
  - `rebaseline`：记基线：读到值即武装（构造时的既有内容不触发）；读不到保持未武装。
  - `poll_at`：一轮观察（时间与系统读数注入，纯逻辑单测覆盖）：取材轮次闩锁置位：消费之并做计数归因——基线到现值的变化数超出本轮自报写盘数，即有轮次内的外来写入（用户的真实复制），保留基线、照常落入前进判定（复查出图像即触发）；否则全部变化都是本应用写的（注入复制与恢复写回），吞掉并就地重记基线。读数失败按保守处理：吞掉重记，不产出观察事件。开关关：不查询（关态零开销）；基线作废，重开时重记——关闭期间的旧内容在重开后不触发。未武装：只记基线，本轮不触发。到节奏才查 changeCount：没前进不动作；前进即消费基线（文本复制不复查 types），复查出图像才产出观察事件，并记下该次变化的 changeCount 供②比对竞态。有外来写入时基线不动，落到前进判定（是图即触发）。
