## 为什么把换装编排抽成共享核心（2026-11-07，Windows 移植 P3a）

- 两平台的换装是同一套机制（腾位、就位、失败回滚、残留清理），差异只在载荷形态与提取/拉起方式；抽成共享核心让回滚语义只有一处定义，系统（Windows）的重命名交换与系统（macOS）的应用包目录交换走同一份代码，行为漂移无从发生。
- 共享核心零平台分支，结构校验与换装策略的单测因此能在任一宿主跑双平台契约（测试构造两种载荷规格），分叉实现的验收不依赖系统（Windows）运行器。
- cfg 分派只出现在更新模块的声明处（`update/mod.rs`），本文件连同测试文件零 cfg，对齐“cfg 只进模块声明文件”的移植纪律。

## 载荷规格用结构体加可选锚点而不用枚举（2026-11-07）

- 形态差异本可用双变体枚举表达，但枚举变体在只构造其一的平台编译时会吃 dead_code 判罚（严格模式警告即失败）；`PayloadSpec` 用 `exe_name: Option<OsString>` 承载形态——有锚点即平铺载荷、缺省即目录载荷，两个分支都是数据驱动的 match 臂，任一平台编译都不产生死代码。
- 代价是语义稍间接，锚点含义在文件头与两实现文件各有一句；换来的是跨平台可编译可测的单一契约。

## 腾位前清残留移入编排内部（2026-11-07）

- 系统（macOS）原实现在解压前清 `.app.old` 残留；收敛后清残留是逐条目、紧贴腾位动作进行的。行为差异：解压失败时不再提前清掉旧回滚副本——解压都没成功就销毁回滚手段本就不合理，新时序顺带修掉这一层。
- 回滚把已就位的新载荷撤下、已腾位的旧载荷复位；回滚本身失败保留现场并带痕迹（与 macOS 原实现的 `.app.old` 保底一致，措辞泛化为载荷）。若无任何腾位与就位发生（首条目腾位即失败），不发回滚日志，避免空转噪音。

## 新载荷缺席的旧旁置文件不回收（2026-11-07）

- 平铺载荷逐文件换装，旧目录里多出来的文件（如旧版曾带的动态库）不删除——删除面（锁、回滚窗口）与本次里程碑的收益不成比例，当前发布脚本保证文件集稳定（可执行文件加旁置动态库）。文件集收缩出现需求时再扩展契约并补测试。
