## 「每上下文都要装」的现状盘点（任务 11 开工时的核查）

- **字体**：两个 egui 上下文各装一次（`fonts::install`，字节已进程内共享，见 fonts_comment.md）。
- **主题**：偏好写在每个上下文的 `options` 上，设置页改一次要写两个（原 `apply_theme_to`）。
- **样式 token**（ui/style.rs）：纯常量，由渲染函数引用，不逐上下文写——不在同步义务内。
- **动画状态、markdown 缓存**：各窗口自己的渲染状态，不该共享，也不在同步义务内。
- 结论：只有字体与主题两条，但它们分散在两个文件、两条调用路径（建帧 vs 偏好变化）。

## 统一装入点的设计取舍

- `new_context` 是**唯一**的上下文建立入口：建完即装好字体与主题，调用方拿不到「半装好」的上下文。
- `reapply` 供运行时偏好变化用（遍历已存在的上下文），`install` 是两条路径共用的施加实现。
- **`install` 里重复施加字体表是安全的**：`FontDefinitions` 按值比较，两次构造（默认表 + 同一个
  `&'static` 字节）内容完全一致，egui 的 `set_fonts` 判定相等即不重建 `FontsImpl`；代价只有一次
  77.9MB 的 memcmp，且只发生在主题变化这条冷路径上。这样「一个函数列出全部每上下文设置」成立，
  不必为省这次比较把字体拆出去（拆出去反而会给「漏装字体」留缝）。
- 字体字节仍由 `fonts` 模块缓存并共享（任务 10），装入点只负责「把已缓存的字节登记进各上下文」。
- **门禁**：约束门禁（拆包后住 `scripts/hooks/constraints/ui_boundary.py`）新增「egui 上下文统一装入点」扫描——除
  `crates/gloss-app/src/ui/context.rs` 外，任何 `.rs` 里出现 `Context::default()` 即失败；
  自测（拆包后 `ui_boundary_test.py`）含两条用例：装入点外裸建被拒、装入点内合法不误报。

## 选中态底色改品牌朱砂（2026-10-12）

- **来龙去脉**：egui 默认 `selection.bg_fill` 是自成一套的蓝，与品牌朱砂色板（style.rs
  `color` 档）不同源——用户反馈「监听剪贴板图片开关与下拉选中项的底色」与保存的浅色系
  不一致。选中态底色是 `visuals.selection` 的全局语义（`selectable_value` 选中行、自绘
  开关的着轨、文本圈选都读它），逐控件改色会漏，收进 `install` 按浅/深两档各覆盖一次，
  随主题偏好取用。
- **备选**：在 `toggle_switch`/各 combo 处局部改色——被否：同语义多处写，新控件默认仍落
  默认蓝；`install` 是唯一的每上下文施加入口，选中态属于「每个上下文都要有」的设置。
- **快照影响**：settings 系基线整体重录一次（提示语加长 + 无选中态可见差异，8 张），
  缘由见同日提交说明；朱砂着轨随同日「监听默认开启」（config_comment.md）进
  settings 基线，开关 ON 态自此有基线锁定。
- **kittest 夹具同源化**：夹具上下文原本只装字体（popup 的首帧钩子）或什么都不装
  （settings 的快照夹具），选中态落 egui 默认蓝——开关进基线后与真机观感分叉，
  基线审阅会误判。`apply_selection_colors` 自 `install` 抽出为独立施加点，
  settings 的两个夹具（交互/快照）与 popup 首帧钩子都调用它；字体仍归
  `install_kittest_fonts`，主题偏好仍归 Harness builder，各管一段。

## 调研一：多 viewport 统一两个窗口（结论：不做）

- egui 支持一个 `Context` 管多个 viewport：`RawInput.viewport_id` 选定 viewport，`run_ui` 每个
  viewport 一次 pass；`egui-winit` 仍是**每个窗口一个 `State`**（其文档即「per viewport/window」）。
- 收益：同步税彻底消失（字体表、图集、字形缓存、样式都只一份）；本任务前这是唯一动力。
- 代价与风险（都在既有不变量上）：
  - 渲染管线要改成「每帧每 viewport 一次 pass + 逐 viewport 的输入/输出路由」；图集增量
    （`textures_delta`）在两个 pass 间共享同一份文字图集，必须只应用一次，否则重复上传。
  - 隐藏窗口的重绘门控（`overlay_repaint` / `settings_repaint` 各自独立）与 L3 首帧预算
    （预创建窗口 + 首帧 < 100ms）都要在 viewport 模型下重新对齐。
  - `Memory` 共享意味着两个窗口的焦点与控件 id 进同一命名空间——今天「浮层失焦 Esc 不再生效」
    这类行为正是靠两个 Context 隔离得到的。
- 触发条件：出现第三个窗口，或「每上下文都要装」的条目显著变多时再评估。

## 调研二：纯英文 locale 下跳过 CJK 字体加载（结论：不可行，改走两条正道）

- **为什么不可行**：内容语言与界面语言无关。界面英文时，选区文本、词卡原词、目标语言产物仍可能
  是中文；一旦不装后备字体，这些内容渲染成豆腐块——L2 快照即「无后备字体」下的形态
  （`tests/snapshots/popup_word_card.png`：UI 文案与词卡释义都是方框，拉丁文正常）。
  `Language::System` 在英文 macOS 上尤其危险：界面英文、用户天天划中文。
- **省下来的量（本机实测，2026-09-23，warm cache）**：
  - 字体字节获取（font-kit：slurp + 就地解包 + 复制）= **4.84s**，常驻 **77.9MB**；
  - 把字体装进 egui（`set_fonts` + 首帧图集）= **6.7ms**；`new_context` 全程 5.73s（几乎全是前者）。
  - 即：昂贵的是「拿到字节」，不是「装进上下文」。
- **两条正道**（都比按语言跳过安全）：
  1. **表紧致化**（遗留 #5）：77.9MB → 13.1MB，同时把 4.84s 的复制量降到约 1/6，行为零变化。
  2. **字节获取移出启动路径**：后台线程加载，就绪后 `set_fonts` 只要 7ms；启动零阻塞，代价是
     首个中文帧之前可能短暂豆腐块（可配合就绪即 `request_redraw` 缩短）。
  两者可叠加；建议表紧致化优先（无观感取舍）。

## `new_context`

- 新建装好基础设置的 egui 上下文——全仓唯一的上下文建立入口。
- 字体只装内置字形快路径（命名字体族恒绑定）：系统字体装载是秒级的，
  不挡首帧，由 [`apply_system_fonts`] 在后台线程装载后补装。

## `reapply`

- 把每上下文设置施加到一批已存在的上下文，返回写到的个数。

## `apply_system_fonts`

- 装载系统字体并补装到一批上下文的字体表（阻塞调用，供启动后的后台
  线程执行）。装载完成前各上下文一直用内置字形快路径；完成后逐上下文
  换完整字体表。重绘不在这里请求——egui 的重绘请求没有跨线程唤醒通路
  （egui-winit 不注册 repaint callback），完成信号由调用方经 Waker 送到
  主线程（`UserEvent::FontsReady`），主题也由主线程按当前偏好重施加，
  装载窗口内的主题变更因此不会被这里的快照覆盖。
- 先走一次完整装载把字体字节缓存填上，下面 install 的就绪判定才会
  选完整定义；字节在 OnceLock 里，重复调用命中缓存。

## `install_fonts`

- 只换字体表：补装路径专用。主题随 `UserEvent::FontsReady` 在主线程由
  reapply 统一施加，这里不碰主题。

## `install`

- 施加全部「每个 egui 上下文都要有」的设置。系统字体字节就位前走内置
  快路径（[`fonts::builtin_definitions`]），就位后走完整定义（字节级
  缓存命中，秒回）。对 egui 上下文的写入都收在这里。

## `apply_selection_colors`

- 选中态底色（下拉选中行、开关着轨、文本圈选）取品牌强调色，浅/深两档
  各写一次，随主题偏好取用，不写则落 egui 默认蓝。kittest 夹具上下文
  （settings/popup 测试）也走它，快照与真机同观感。

## `theme_preference`

- 配置主题 → egui 主题偏好（出厂跟随系统，设置页可固定明/暗）。
