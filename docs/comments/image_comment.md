## 上移平台中立共享层（2026-11-14，方案 A4 P2）

- 图片归一化的预算判定、降采样、便携式网络图形（PNG）编码与一轮读取的
  “竞态→交付不出→解码”三路，此前在系统（macOS）与系统（Windows）两侧
  同构双份（镜像意味着修一处漏一处）。整体上移 `common/image.rs` 只写
  一份：平台目录只留格式映射与取数原语（计数读数、交付与映射闭包），
  系统独有的数据形态变换（系统（Windows）的位图头合成）也留在平台侧；
  共享层零目标条件编译、零外部函数接口（FFI）、零不安全块（定案 K3）。
- 接缝形状（交付风格 `DeliveredFlavor`）：交付闭包返回预算口径的交付字节
  长度、解码格式与载荷借用视图三件——预算按交付字节判（与两侧既有口径
  一致），载荷经借用直通解码，共享层不复制图像字节。系统（macOS）的
  零拷贝（粘贴板数据直通解码）与系统（Windows）的位图文件字节单次合成
  （映射闭包内合成、以持有态随交付风格走出闭包）都由这个形状承载，两侧
  分配次数零变化。
- 取数原语统一为“交付可失败”形状：系统（Windows）的超限风味在交付闭包
  报尺寸错误（锁页与拷贝之前判，原样上抛），系统（macOS）的交付不可失败
  （包一层成功态）。观察比对先于交付闭包的不变量随三路上移——竞态时
  不读内容（内容读取才触发系统（macOS）“允许粘贴”授权；系统（Windows）
  侧为不取数据字节）。
- 两条静默丢弃路径的日志文案随共享单源统一措辞：板不可读（debug）与
  交付不出（warn）的名词统一为“clipboard”，系统（macOS）交付不出文案
  不再点名“粘贴授权可能被拒”——级别与分支条件零变化，授权成因的排查
  指引由系统（macOS）绑定模块头与本记录承载；竞态文案两侧本就逐字一致。
- 取材字节预算随本模块单源：四个图片预算常量（交付字节、像素面积、产物
  字节、产物最长边）与选中文本字节上限（`MAX_SELECTION_BYTES`，两侧选区
  读取器此前各自定义同值常量）一并收进共享模块，改数值只有一处。
- 测试随逻辑迁移一份锁两平台：原两侧镜像登记共 32 条合并为共享模块一节
  14 条加两侧绑定节 6 条——共享管线闸门（字节、面积、截断、降采样）以
  便携式网络图形（PNG）夹具单份锁定（两端目标同有该解码特性面），位图
  家族独有的头变体与行序测试留在系统（Windows）侧、标记图像格式（TIFF）
  映射测试留在系统（macOS）侧；超限风味上抛一条随“交付可失败”形状升为
  共享。头闸门夹具改用补丁便携式网络图形（PNG）头块尺寸并重算头块校验
  和（原两侧各补丁本族格式头，无校验和；共享夹具两端同可用）。

## decode_to_png 的三级设界（评审 HIGH 修订）

- **为什么设界逐级前置（交付字节 → 头尺寸 → 整图解码）**：过去式炸弹
  （tiny_tiff/小 PNG 声明巨大尺寸）的危害在“按声明值分配”，声明值在头
  里。交付字节上限（64MiB）卡住编码数据本体；`into_dimensions()` 只读
  头拿声明尺寸，像素面积上限（4096²）在**任何大分配发生之前**拒绝超限；
  两关都过了才整图解码——合法满尺寸图像的解码峰值约 1.5–2 倍位图（解码
  中间缓冲 + RGBA 转换，约 100MB 量级），pastebomb 则是零大分配拒绝。
  产物侧仍有 PNG 字节上限（20MiB）。
- **为什么上限是这些数值**：交付 64MiB——恰好 4096² 的未压缩 TIFF
  （RGB8）约 43MB，给满尺寸合法图像留量；面积 4096²（16MP）——4K 屏
  截图（8.3MP）在内，RGBA 位图恰达 64MB，超出即视为攻击性输入；PNG
  20MiB——主流 LLM API 图像上传的常见门槛量级。都是源码常量，报错不
  截断——截断产物是静默数据损失。
- **为什么用 `ImageReader::with_format` 显式指定格式而不是 `with_guessed_format`**：
  读的是哪个风格已经确定（格式映射由平台侧定案），猜格式多一次内容嗅探
  且对截断输入可能猜错格式、把“截断”误报成“不支持的格式”。
- **为什么解码失败按读取失败（`ImageUnavailable`）而不是 ImageTooLarge**：
  头声明了合法尺寸但数据残缺，说明来源损坏（读到的不是一张完整图），不是
  “图太大”——错误类别要给用户正确的心智。头解析失败同理（哨兵已见图像
  风格，读到却解不开，属取材失败）。

## read_with（三条分岔，2026-10-10 整体验收修订；上移随方案 A4）

- **为什么竞态落 `Ok(None)` 而不是自定义错误变体**：竞态不是故障——下游
  不该有“失败”可观察（不弹卡、不占失败文案），但也不能混入 `Ok(Some)`
  的成功路径。`Result<Option<_>, _>` 三态恰好一一对应成功/静默/失败。
- **为什么交付不出单列 warn 分支**：板上声明了图像却读不出数据与“板上
  已无图像”同形，混进竞态会把成因伪装成“剪贴板已变化”误导排查，debug
  级在默认 info 过滤下零痕迹。分岔收进共享读取器：竞态（观察比对不过）
  debug、且不读内容（比对先于交付——内容读取才触发授权）；交付不出
  warn 留痕，`just logs --level warn` 有痕可筛。各侧成因（系统（macOS）
  为 15 及以上版本“允许粘贴”授权被拒、系统（Windows）为板被短时占有或
  数据查询失败）见两侧绑定记录与模块头。
- **为什么授权拒绝落静默丢弃而不是失败卡**：设计 §9 对拒绝路径只要求
  “失败卡或静默+日志”二选一。用户刚明确拒绝授权，紧接弹一张失败卡是对
  拒绝行为的二次打扰；warn 留痕已满足可观察。若日后要改失败卡，落点是
  交付闭包加一个错误分支，读取器签名不变。
- **为什么系统读数走注入（`read_with` 的三个闭包）**：竞态/无数据/不可
  观察三个分岔的落点（丢弃 vs 上抛、先比后读的次序）是行为契约，注入后
  纯逻辑单测锁定（与哨兵源 `poll_at` 同型）；生产 `read` 只是把各自平台
  的读数与交付原语喂进同一条路径（见两侧绑定记录）。

## encode_png（RGBA → PNG）

- **为什么快速压缩档（`CompressionType::Fast` + `FilterType::NoFilter`）**：
  编码在事件线程上同步执行，时长直接挂在“复制 → 弹卡”链路上；PNG 压缩
  的收益端在磁盘/网络，而这里的产物只活一跳——出网请求体（base64 后即弃）
  与内存会话。Fast+NoFilter 对照片类内容比默认档省一半以上编码时长，
  体积多出约 10–30%，换取弹卡延迟，划算。若将来缓存把 PNG 落盘（现行方案
  不落盘），再按落盘口径换档。
- **为什么 RGBA 缓冲与尺寸不符按读取失败而不是 ImageTooLarge**：不符说明
  来源数据损坏，是“读到的不是一张完整图”，不是“图太大”——错误类别要
  给用户正确的心智（重试大概率同样失败 vs 换张小图）。校验在前，
  `write_image` 的内部校验是第二道闸。
- **为什么不先经 `RgbaImage::from_raw` 而直接 `write_image(rgba, …)`**：
  from_raw 需要拿走 `Vec<u8>` 所有权，必然整块拷贝一次 RGBA；`ImageEncoder::
  write_image` 接受裸切片，零额外拷贝（大缓冲区不冗余克隆条目）。

## 符号契约（自代码注释迁入）

- `MAX_FLAVOR_BYTES`：交付字节上限：恰好 4096² 的未压缩 TIFF（RGB8）约 48MB，给满尺寸的合法图像留量；超限在头解析之前整体拒绝。系统（Windows）侧同值口径在交付原语前置（锁页与拷贝之前），本闸门是其第二道。
- `MAX_PIXELS`：像素面积上限：4096×4096 ≈ 16MP（4K 截图 8.3MP 在内）；面积在上限处的 RGBA 位图即 64MB，超出即视为 pastebomb。
- `MAX_PNG_BYTES`：PNG 字节上限：取材产物进 `TaskInput`、缓存会话与出网请求体，超限整体报错。
- `MAX_PRODUCT_SIDE`：产物最长边上限：取材产物经 base64 出网并入缓存会话，超过即按比例缩到上限内——视觉模型内部本就会把输入压到 ~1MP 一档，上限外的像素只有编码与传输成本；1536 长边覆盖图表与截图文字的判读质量，同时把解码后的 GPU 纹理与 base64 请求体的量级压到 ~9MB 档。上限以内的产物原样编码（不放大、不重采样）。
- `MAX_SELECTION_BYTES`：选中文本字节上限：两侧选区读取器（辅助功能（AX）与用户界面自动化（UIA））共用的取值缓冲分配上界，随取材字节预算在本模块单源；取值缘由见两侧选区读取器记录。
- `flavor_within_budget` / `pixels_within_budget` / `png_within_budget`：各预算是否在限内（纯逻辑，单测覆盖边界）。
- `downscaled_dims`：超限产物按比例缩到最长边上限内的目标尺寸（纯逻辑，单测覆盖）：上限以内返回 `None`（原样编码）；缩放按比例四舍五入、至少保留 1 像素。
- `DeliveredFlavor`：交付风格：平台侧格式映射的产物，共享管线的输入——`flavor_len` 是预算与日志口径的交付字节长度（载荷经映射后可能与交付字节差一个文件头，预算判交付口径），`format` 是解码格式，`payload` 是载荷视图（借用直通解码，或合成文件的持有态）。
- `decode_to_png`：交付风格 → 解码 RGBA → 超长边降采样 → PNG（快速压缩档：编码在事件线程上执行，时长直接挂在触发到弹卡的链路上）。设界依次执行：交付字节上限在头解析之前，像素面积上限以仅读头的尺寸判定、先于整图解码，超 `MAX_PRODUCT_SIDE` 的产物按比例降采样，PNG 字节上限判在编码产物上。超限整体报 `ImageTooLarge`（不截断）；头不可读、解码失败、缓冲与尺寸不符都按读取失败处理。解码器构造两次是像素预算闸门的代价：先只读头取尺寸，超限的图不进整份解码（解压炸弹不该先吃掉内存再被拒），通过后才整份解码。
- `header_dimensions`：只读头取尺寸：超限的图在整份解码之前就被像素预算拒掉（解压炸弹不该先吃掉内存再被拒）；头不可读按读取失败处理。
- `decode_rgba`：整份解码为 RGBA8：已是 RGBA8 的图 `into_rgba8` 原地取出，不再整份复制。
- `downscale_to_budget`：超长边的产物按比例降采样到上限内，预算内原样归还。
- `encode_png`：RGBA 位图 → PNG。缓冲与声明尺寸不符按读取失败处理（校验在前，`write_image` 的内部校验兜底）。
- `header_unreadable` / `decode_failed`：头不可读与解码失败的留痕出口：debug 留痕后统一映射 `ImageUnavailable`（读取失败变体，指引重新复制）；平台侧映射闭包的格式非法路径复用 `header_unreadable`。
- `SystemImageReader`：剪贴板图片取材读取器（共享形状）：核心层剪贴板图片取材端口的实现类型，两侧共用同一类型，观察记录句柄由同一次装配的哨兵源交给构造；端口实现绑定各自的取数原语（见两侧绑定记录）。
  - `new`：观察记录句柄来自同一次装配的 `ClipboardWatchSource::observer`。
  - `read_with`：一轮读取（共享注入点：计数读数、交付与映射三个闭包由两侧端口实现注入，纯逻辑单测覆盖三条分岔）：板不可观察：读取失败上抛；计数与①观察记录不一致：①②之间被覆盖，竞态静默丢弃，不调交付闭包（比对先于内容读取）；交付闭包报错（如超限风味）原样上抛；板上声明图像却交付不出数据：warn 留痕后静默丢弃；可交付：映射后解码为 PNG。

## 产物最长边 2048 降采样（2026-10-16）

- 视觉模型内部会把输入压到 ~1–1.5MP，上限外像素只有编码与传输成本；
  base64 出网体积约缩 4×，图片任务的传输段 TTFT 与缓存会话同步受益。
  像素面积上限（4096²，pastebomb 闸门）与 PNG 字节上限不变——降采样只
  作用于已放行的产物。（最新沿革见上移节：上限现为 1536。）
