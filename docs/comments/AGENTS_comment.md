## 注释纪律（规则脚本挂类别，2026-10-26 四次改写）

- 起因：上一版把六个脚本路径直接写进 AGENTS.md。路径仍是「文档里的一份副本」——脚本
  改名、拆分或合并，文档不会自己知道；而速查工具按目录扫描、顺序由文件名决定，与文档
  的条目顺序无关，两边各自维护一份「谁管什么」。
- 做法：类别到脚本的对应收进 `scripts/dev/comment_rules.py` 的 `CATEGORIES` 表，这是
  全仓唯一一份。每条记录类别标识、类别名与一至多个脚本路径；放行标记多一个开关，额外
  读 `gate_report.py` 的常量。类别按文档条目顺序排列。
- 命令行为：不带参数打印类别索引与全部规则原文；带类别名或标识只读一类；未知类别退出
  2 并列出有效名；脚本缺失、文件头缺失或不可解析退出 3（失败关闭，已打印的部分不作
  完整性保证）。
- 文档侧：六个条目删掉全部脚本路径，只留类别名——黑体名即命令参数，读者用
  `just comments-rules 源码` 一次拿到脚本路径与规则原文。原先单列的「测试面」并入
  「源码」：它在工具里没有独立脚本，单列会造出一个不能当参数用的黑体名。
- 取舍：文档不再能离线回答「源码注释由哪个文件判」。接受，因为路径是最易漂移的一类
  事实，而速查命令在本地与持续集成都可用。
- 未采纳：让工具反向校验 AGENTS.md 的类别名。标题词太通用（「源码」全文件出现几十次），
  按标题匹配假阳性高，按段落切分又引入对文档结构的解析依赖。漂移防线改为兜底行为：
  未知类别报错并列出有效名。

## 注释纪律规则速查（工具读文件头，2026-10-26 三次改写）

- 起因：判据外移后，读者要连开六个文件才拼得出全貌；文件头本来就是中文写的规则清单，
  缺的只是一个一次读完的入口。
- 做法：新增 `scripts/dev/comment_rules.py` 与配方 `comments-rules`——按载体顺序打印
  判罚脚本的模块级文档字符串，静态解析（`ast`），不执行被读脚本；另打印
  `ALLOW_REASON_MARKERS` 常量的现值。标记名是唯一不在任何文件头里的事实，故从常量读，
  不抄第二份。
- 边界：工具不缓存、不落盘、不生成文档；文件头缺失即退出 1（失败关闭），避免「打印了
  一半当全量」。
- 仍只住在 AGENTS.md 的两条：`lines:allow` 的落点（挂质量条目总表「文件行数上限」）、
  记录文件的命名与锚定（记录目录不进版本库，没有门禁承载）。

## 注释纪律（判据外移，2026-10-26 二次改写）

- 触发：上一版把门禁判据（文件头五项条件、SAFETY 三项约束、五类放行标记、`lines:allow`
  前五行、标记语言逐行判罚）复述进 AGENTS.md，等于给每条规则造了第二份事实源——脚本
  一改，文档立刻说谎，且没人会记得同步。
- 做法：本节退为索引。六个归口条目只给「载体 → 判罚文件」，判据本身一个都不抄；新增一句
  优先级：判据以判罚脚本为准，本节与记录文件只是说明，冲突时以脚本为准。
- 归口：受检面与分派 → `check_comments.py`；源码 → `check_rust_comments.py`（中文区与
  英文区共用判据在 `language_spec/chinese.py`、`english.py`）；脚本与配置 →
  `check_script_comments.py`；标记语言 → `check_docs.py` 加 `language_spec/coderef.py`，
  排版归 `rumdl.toml` 与配方 `lint-md`；放行标记 → `gate_report.py`；`lines:allow` 落点
  仍挂质量条目总表「文件行数上限」。
- 留在本节的两块，是确实没有脚本承载、也无处可指的政策：① 代码只留两类注释、其余进
  记录文件（这是取向，不是判据）；② 记录文件的命名与锚定（记录目录不进版本库，没有任何
  门禁会检查它）。
- 取舍：读者要写合规注释得去读脚本；可接受——脚本头部的中文文档字符串本来就是规则清单，
  门禁报错又直接给规则标识与修复指引，比文档里一份会过期的摘抄更可靠。

## 注释纪律（整节重写，2026-10-26）

- 触发：按清晰性、一致性、完整性、可执行性四条审查原节，发现原则与方法互相拆台、
  门禁实际放行的形态大面积缺席。原节四句话要覆盖三路门禁（源码、脚本与配置、标记
  语言文档），信息密度与判罚面不对等。
- 修订的七处硬伤：① 原则写「注释只写代码说不出的东西」，方法却只留文件头与不变量
  注释——按原则写必被门禁拒；改为「代码里只留两类注释，其余进记录文件」，与门禁
  同向。② 五类放行标记（`constraints:allow-context`、`secrets:allow`、`lines:allow`、
  `i18n:allow`、`deps:allow`）原节只字未提，而质量条目总表两处正在使用；按原节字面
  它们都属「其它注释」，应迁记录文件。③ 文件头的可执行条件（`//!`、必须存在、逐行
  含汉字、禁反引号与章节号、只许在代码之前）全部缺席，「只写功能概述」无法据此判定。
  ④ `// SAFETY:` 只说「紧贴、写明不变量」，漏了纯英文这条硬条件——其余注释一律中文，
  照写必违规；「紧贴」也补成「不夹空行、其它注释或完整语句」。⑤ 测试面完全缺席，而
  「测试」节要求层标签落在测试目标文件头，两节之间没有桥。⑥ 脚本与配置、任务配方的
  单行注释、标记语言文档逐行受检（含本文件）三块要么没写、要么一句「其余文件」带过。
  ⑦ 记录文件一句塞了命名、锚定、冲突前缀、同步、版本库边界、指针六件事，且没有复查
  入口（`just comments`）。
- 保持不动的判断：原节「重述型注释一律删除」保留（换成「不是少写，是不写」）；why 型
  内容仍然只进记录文件、不进代码——本次只把这条讲清楚，不改分工。
- 结构改为「原则 + 受检面 + 四类载体（源码、脚本与配置、标记语言文档、记录文件）」，
  每类只写门禁能判的形态，避免再出现「原则鼓励、门禁禁止」的双轨。
- 仍未采纳：上节「待议」两条（跨线程不变量旁注入例外、`// SAFETY:` 引用符号须可检索）
  状态不变。

## 注释纪律（新增「重述型注释一律删除」，2026-10-17）

- 背景：一次全仓注释审计（5 个分区、约 3.5 万行生产代码）给出两类发现——① 重述型
  占位注释成批存在，根源是 `missing_docs` 门禁把「必须有注释」变成了形式要求；② 30+
  条「为什么」型注释与本节「描述行为，不解释动机」的字面冲突。审计同时附了一份通用
  最佳实践的对照意见（why > what；重述型注释应删除；注释写给经验最少的维护者）。
- 采纳对照意见里的「重述型注释一律删除」：它与本节唯一判据（长期维护价值）同向，不
  改变「为什么进记录」的分工。落为新增一条纪律，并在质量条目总表的「注释纪律」条目
  里点出。配套移除 `missing_docs` 门禁（决策记录见 `Cargo_comment.md`），否则该纪律
  与门禁互斥。
- 不采纳对照意见里的「why > what」：本仓保留「描述行为，不解释动机」。why 型内容的
  归宿是 `docs/comments/`，不进代码注释——本仓有整套记录机制承接它，且 why 型注释随
  代码漂移后极难被察觉（审计里失效的符号引用大多正落在 why 型注释上）。
- 连带改写：测试代码禁止注释的例外项原写作「`missing_docs` 门禁强制的 crate 级 `//!`
  文档」，门禁移除后改为按「测试」节的层标签要求表述，避免例外挂在一个已不存在的机制上。

## 记录文件入库与命名门禁（2026-10-27）

- 决策：docs/comments/ 随仓库跟踪（`.gitignore` 加 `!docs/comments/` 例外），并发覆盖类事件从此有版本历史可回溯；上文两次改写里「记录目录不进版本库、没有门禁承载」的状态自此作废，记录文件节的命名约定随之改写为映射脚本的说明。
- 命名治理：映射规则单一事实源住 `scripts/dev/comment_map.py`——同一源文件一对记录（决策与测试），mod 文件取父目录名，跨文件同名与自由主题记录在其登记表显式登记；`just comment-name` 从源头拿对名，`just comments-doctor` 全量体检。注释门禁路由接入记录名三道判罚（名字合法性、陈旧、撞名），陈旧记录一律删除——2026-10-24 那批带后缀命名的根因（口头约定对并发会话不可靠）由机器拦住。
- 入库清理：十二个解析不到源文件的陈旧记录删除（含 `main.rs_comment` 那批的遗留与已删除模块的孤儿），两条续篇按查重合并进规范名文件，两条随源改名走 git mv 同步改名；前言里「随 docs/ 整目录本地维护」措辞全量改写。

## 提交与拉取请求书写门禁（整节重建，2026-10-31）

- 起因：门禁流程收口计划（`docs/plans/gate-process-closure-plan.md` 阶段 6）走查发现旧节「三个作业都是必需检查」与分支保护实际清单漂移（评审结果检查不在其列），#280 先把过时节整节移除，约定收口计划末段一次改齐重建。
- 做法：必需检查清单不复抄名单，托管平台 `main` 分支保护的必需状态检查清单即单一事实源，核对入口写为保护接口一条查询；生效语义按计划统一口径写全两级（闸门、红牌），评审结果门禁与内容快照锁定按闸门记、行内评论检查按红牌记，并写明合并完成后编辑只能红牌的边界；创建前预检流程（起草、`just pr-lint-draft`、绿灯后 `gh pr create`、`just pr-lint` 复检）取代旧节「开 PR 后立即本地跑 pr-lint」的事后约定；高频判罚点三条原样保留（#274 登记，不在本次改动面）。
- 取舍：不复抄名单接受「文档不能离线回答哪些作业是必需检查」，换取名单不再有第二份会漂移的副本——旧节的漂移正是复抄所致。本节初版曾挂对账门禁（阶段 1 脚本）做应然与实然的差集核对，该脚本随阶段 1 回退移除（阶段 5 快照脚本对其的解析单点复用一并内联），名单核对回到接口直查。
- 状态注记：评审结果检查的必需检查补设属托管平台配置动作，由管理员完成。
