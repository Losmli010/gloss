## 空选区让渡耗尽后落剪贴板兜底（2026-10-01，修订「不兜底」决策）

- **为什么推翻 2026-09-30 的「不兜底」**：那次修的是 0–30ms 的时序竞态，
  让渡补读确实治好了它；但同日的真机日志（20:28–20:32 连续 14 划 11 空）
  证明还有第二类现场——一部分应用（无障碍树未激活的 Electron/Chromium、
  不暴露选中文本的自绘应用）对**真实划词**也稳定回「属性在而无值」，4 次
  读取跨 360ms 全空。对这类应用，让渡到天荒地老都是空，「不兜底」等于
  永久放弃它们，而用户看到的正是「弹窗闪现即消失」。
- **为什么当初的「陈旧剪贴板冒充」顾虑今天不成立了**：`ClipboardFallbackReader`
  的确认写入语义（快照基线 → 注入 Cmd+C → `PasteboardSynchronize` 报
  modified 才采纳 → 未确认即 `SelectionUnavailable`）已经在结构上回答了
  它——误滑时 Cmd+C 无物可写，剪贴板不变化，不确认就不采纳，陈旧内容
  冒充不进来；真误滑的收口从「SelectionEmpty 静默收回」变为
  「SelectionUnavailable 静默收回」，状态机侧两个变体本来就在同一个分支。
  「不兜底」是把确认写入已解决的问题当成了悬而未决。
- **残余代价（明示接受）**：真误滑会注入一次 Cmd+C 并把事件线程占用至多
  ~4.2s（两轮确认，与既有 Unavailable 兜底同阻塞语义）；个别把 Cmd+C 绑
  定为中断的终端环境会收到一次中断信号（同一风险面，既有兜底路径早已
  存在）；确认窗口（≤2s）内其他进程恰好写剪贴板的极小概率误采纳。生产
  裁决：真实划词的判定率远比误滑的收回速度值钱，且误滑的完整修复在
  状态机层（探测—提交两段式，误滑根本不出窗，见 machine_comment.md）。
- **可观测性**：预算耗尽落兜底时记一条 info（`selection still empty after
  settle budget, falling back to the clipboard`）——它是「哪个应用是 AX
  盲区」在默认日志里的第一现场，与壳层误滑日志（带前台应用标识）配套
  定位。

## 空选区的让渡补读（2026-09-30，弹窗快速关闭）

- **问题现场**：用户反馈「划长句翻译或代码时弹窗快速关闭」。日志实证：
  2026-09-30 14:47–15:00 连续十余次 `empty selection` 收回，距取材开始
  0–30ms——鼠标释放瞬间 AX 查询立刻返回「属性在而无值」，真实划词被
  `accept_failed` 的手势静默收回分支吃掉（弹窗亮起即消失）。短选区无感
  （应用同步更新选区），长选区/代码编辑器处理选区更慢，时序差才显形。
- **修在哪一层**：platform 的组合读取器，不是状态机。「空选区＝误滑」
  的语义在 `machine::accept_failed` 仍然成立（误滑收回足够快、不弹卡），
  错的是 platform 在时序竞态里把「还没写好」报成了「没有」。状态机与
  壳的分支、日志、语义一律不动。
- **为什么不让渡后落剪贴板兜底**：空读是「属性在而无值」的如实回答，
  注入 Cmd+C 会把剪贴板陈旧内容冒充成选区（既有决策，模块注释在案）；
  让渡补读绕开了注入，读到的仍是 AX 的第一手回答。
- **预算取舍**：`EMPTY_READ_ATTEMPTS = 4`（首读 + 3 补读）× 120ms ≈
  360ms 最坏让渡，全部发生在事件线程（与剪贴板兜底最坏 4s 同一阻塞
  语义）。真实误滑的骨架会因此多亮几百毫秒——用它换真实划词的判定率，
  两侧都远低于可感知打扰的量级。
- **让渡策略参数化**（`delay_for`）：`combine` 把「第几次空读后让渡多久」
  收进闭包，测试零睡眠直达时序断言（`settle_delay` 本身另有纯函数测试）。

## 取材边界的 trim 归一化（`normalize`，2026-10-11，方案 15 步骤 1b）

- **为什么归一化点选在组合读取器入口**：AX 读取器（`interpret`）保持
  「读到什么报什么」——它对纯空白透传的既有测试（原样透传不裁剪）仍然
  成立，读取器只如实报告；归一化是取材边界对产物的收口，放在
  `CompositeReader::read`（生产端文本取材唯一入口，AX 与剪贴板兜底两条
  通道的产物都经它出去）一处即覆盖全链路。下游（内容闸门
  `guard::detect_sensitive`、原文视图、prompt 渲染、缓存 key）消费的是
  同一个 `TaskInput::Text` 值，无需各自 trim，也不存在「两处 trim 漂移」。
- **为什么纯空白不走让渡/兜底而直接 `SelectionEmpty`**：让渡补读与剪贴板
  注入服务的是「读不到/还没写好」（空读有二义性）；AX 报出空白文本是
  一次**成功且有内容的读取**，结论已定——选区就是纯空白（误滑），再花
  360ms 让渡 + 最坏 ~4.2s 注入只会白占事件线程。剪贴板兜底即使确认写入
  了空白，修剪后同样落 `SelectionEmpty`，结果不变、时延白付。
- **收益面**：修复前纯空白选区会一路走到 `InputReady` → 触发真实 LLM
  任务（把空白发给模型）；修复后误滑在取材边界即按既有空选区语义静默
  丢弃，与状态机侧「划词空选区不弹卡」的分支（`commit_probe_failed`）
  天然衔接。附带收益：缓存 key 只认修剪后文本，重复划选同一段文字（
  两端拖选差异）能命中同一份缓存。
- **形态**：纯函数 `normalize(raw) -> Result<String, GlossError>` 与
  `combine`/`settle_delay` 同款测试形态（纯逻辑单测，`read` 本身要 OS
  不进单测），`read` 用 `and_then` 组合——组合行保持零逻辑。
- **评审收敛（2026-10-11，LOW）**：`normalize` 不再无条件 `to_owned()`——
  `trim()` 只削两端，`trimmed.len() == raw.len()` 即未修剪，此时把原缓冲
  原样归还，确有修剪才物化新串。选区文本可达 8MB 上限
  （`MAX_SELECTION_BYTES`），多数划词本无两端空白，省掉的是热路径上的
  整段克隆；行为契约不变（既有单测原样覆盖两个分支），故不加测试。

## 激活闸门（`wake_then`，2026-10-12）

- **为什么激活放在「兜底之前」而不是「首读之前」**：激活含跨进程属性写
  入（对宿主的写操作），未走到就不该有副作用——AX 一读就有结果的绝大多数
  手势（原生应用、已开树的 Chromium）必须零接触；只有 AX 让步（空读让渡
  预算耗尽 / 硬错）才问一次激活器。放在兜底之前则是收益排序：兜底是注入
  按键 + 写剪贴板 + 恢复的破坏性路径，若激活能让树回答，就整条跳过。
- **为什么唤醒只在「刚注入成功」时补读**：`wake` 返回 false 的三种情形
  （pid 已评估、非 Chromium 宿主、注入失败）里树都不会变，等待是纯浪费；
  只有刚注入成功时宿主才开始异步建树，空结果才有「还没建好」的二义性，
  才值得花激活预算（5 × 250ms ≈ 1.25s）等它。
- **为什么激活后读到硬错（非空非拒绝）不烧预算**：建树期间的过渡态表现
  为空读（属性无值）；返回硬错说明宿主明确拒绝或链路不可用，等待不会改
  变结局，立即落兜底把总时延守住。
- **为什么唤醒与兜底都收成惰性闭包**：与 `fallback` 同款纪律——闭包里
  是跨进程写/按键注入这类副作用，测试注入 `never_wake`/计数闭包即可断言
  「未走到不求值」，不需要真机。
- **时延账**：最坏路径（Chromium 宿主、树始终建不起来、兜底确认写入也
  超时）比旧路径多 ~1.25s + 数次 AX 往返；但该手势只发生一次（激活按
  pid 记忆），且多数真实划词在激活后 ~300ms 内直接拿到文本，替代的是旧
  路径「注入 + 确认写入（最坏 ~4s）+ 剪贴板副作用 + 恢复写回」，净收益
  为正。预算数字改动时同步 `docs/tests/bdd.md` 与源码常量两处口径。

## 评审收敛（2026-10-12，PR #176 审查）

- **补读环的权限缺失分支**：`wake_then` 原初版本只有 Ok/Empty/其余三分
  支，`AccessibilityDenied` 会落进「其余」被送去兜底——与让渡环「权限
  缺失原样上抛、不兜底」的降级边界相反（兜底靠注入，未授权时注入被系
  统静默忽略，白等超时）。可达性极低（需补读窗口内 TCC 权限被撤销），
  但同文件两个环对同一错误处置相反属会被照抄的边界不对称，补上同款
  分支并以测试锁定（`a_woken_tree_that_loses_permission_propagates_the_denial`）。
- **激活闸门自身的每手势成本记账**：pid 去重必须先拿 pid，故每个落兜
  底的手势在闸门处至少有一次 systemwide 创建 + `AXFocusedApplication`
  跨进程读 + 本地 GetPid——典型亚毫秒，最坏受全局 1s 消息超时兜底，
  占比远小于其后的兜底注入本身；pid 已记账（去重必拒）时后续检测与写
  入都不发生。这是去重语义的内在成本，无法再省。

## 弹窗时延优化：让渡节奏、唤醒常客与等待预算（2026-10-16）

- **数据**：本机 7 天生产日志（123 次成功划词）取材段 p50=434ms / p90=2.5s /
  max=9.4s；89% 的划词先烧满固定让渡预算（3×120ms）再靠唤醒救回，让渡环
  在全量日志中没有一次「等来迟到选区」的贡献——纯过路费。
- **几何节奏** `[25, 75, 150]`（总睡眠 250ms）替换固定 120ms×3：多数宿主
  数十毫秒内落定选区，早密晚疏同预算下覆盖面不缩水。
- **唤醒常客（rescued 记账）**：注入唤醒救回过的 pid 记为常客，此后空读
  跳过让渡直接进激活补读；常客的重注入放行（注入幂等，Chromium 会自行
  收树，重注入是空读后的唯一自救通道）。预期把主导路径（p50）压到
  ~120ms。误记的代价只是换条路走（激活→兜底），不损正确性。
- **AX 等待总预算 700ms**：让渡与激活补读的睡眠段共享（自进入读取起算），
  耗尽即停睡转进。尾部（AX 单次调用最长 2.3s、p90 2.5s）由此钉死；读调
  用本身受 0.3s 消息超时约束。**明示接受**：首次激活恰逢宿主慢建树
  （>700ms）的手势会提前落剪贴板兜底（原有确认写入把关，正确性不变，
  代价是有剪贴板副作用的路径更常出现——换来 p90 进 1s）。
- **产物/收尾分离（SelectionRead/SelectionSettle）**：兜底轮的恢复写盘与
  写盘归因移出取材关键路径（大图剪贴板的快照/恢复可达数十至数百毫秒），
  调用方在 InputReady/TaskFailed 上抛之后 finish。panic 展开的恢复兜底由
  PendingRestore 的 Drop 保留——finish 前炸掉照旧恢复。

## 符号契约（自代码注释迁入）

- `EMPTY_SETTLE_SCHEDULE_MS`：空读让渡的几何节奏（毫秒）：鼠标释放到目标应用把选区写入 AX 属性之间有时序差（长选区、代码编辑器更慢），释放瞬间读到的「空」多半是还没写好而不是没有；多数宿主在数十毫秒内落定，按几何间隔补读，早密晚疏。让渡在事件线程上睡眠，与剪贴板兜底的阻塞语义同款（节奏表总睡眠 250ms，远小于兜底路径的最坏两轮确认窗口）。
- `ACTIVATION_SETTLE_DELAY`：激活补读之间的等待时长：注入开关后宿主异步建无障碍树（数百毫秒起），补读之间让宿主建一会儿。等待在事件线程上睡眠，与让渡的阻塞语义同款。
- `ACTIVATION_SETTLE_BUDGET`：激活补读次数上限：最多 5 次 × 250ms ≈ 1.25s 建树等待（实际受 `AX_WAIT_BUDGET` 的 700ms 整体截断，故最坏睡眠约 0.7s；各次 AX 往返耗时另计，宿主不响应时受 AX 消息超时兜底）。只发生在「激活注入首次成功」的那一个手势，换的是此后所有手势免按键注入、免剪贴板副作用。
- `AX_WAIT_BUDGET`：AX 等待段的总预算（墙钟，自进入读取起算）：让渡与激活补读的睡眠段共享，预算耗尽即停睡转进——让渡段转激活闸门、激活段转兜底。兜底（剪贴板注入确认）有自己的确认窗口，不占本预算。
- `settle_delay`：第 `attempt` 次空读后的让渡时长；节奏表耗尽返回 `None`（纯逻辑，单测覆盖）。
- `activation_delay`：第 `attempt` 次激活补读空结果后的等待时长；预算用尽返回 `None`（纯逻辑，单测覆盖）。
- `Pacing`：让渡与激活的节奏与等待预算（纯旋钮捆包）：`settle` 是空读让渡的节奏，`activation` 是激活补读的节奏，`waits_exhausted` 是两者共享的墙钟预算——把节奏参数化，测试零睡眠直达时序断言。
- `combine`：组合判定（纯逻辑，单测覆盖）：AX 成功直接采纳；权限缺失原样上抛且不评估激活与兜底（见模块注释）；空选区在唤醒常客宿主（`responds_to_wake`，读取入口现读一次）上跳过让渡直接进激活补读，其余按 `settle_delay` 让渡后补读，预算耗尽仍空与「其余读不到的情形」一样先过激活闸门（`wake_then`），激活落空才落到兜底结果。`wake` 是惰性求值——激活含跨进程属性写入，未走到就不该有副作用；`fallback` 同理——兜底路径含按键注入。
- `wake_then`：激活闸门（纯逻辑，单测覆盖）：`wake` 报「无需补读」（该宿主已评估过、不是 Chromium 家族或注入失败）时立即落兜底，不花任何等待；刚注入成功时按 `activation_delay` 的节奏补读，树一回答就采纳，预算耗尽仍空或读不到再落兜底——补读期间宿主建树是异步的，空结果多半是还没建好而不是没有。等待预算在补读之间生效，耗尽即落兜底。补读中权限缺失与让渡环同款原样上抛：注入会被系统静默忽略，兜底只会白等。
- `normalize`：取材边界的归一化（纯逻辑，单测覆盖）：读到的文本修剪两端空白后放行，判空用修剪后的值——纯空白选区（误滑）按既有 `SelectionEmpty` 语义上抛。AX 与剪贴板兜底两条通道的产物都经此收口，让渡补读与兜底注入只服务「读不到」，不为已知纯空白的选区再花时序预算。两端本无空白时原缓冲原样归还，不复制整段。
- `SelectionRead`：一次划词取材的产物：文本语义与兜底轮收尾分离。产物先行（`outcome` 上抛即触发弹窗链路），收尾随后——兜底轮的恢复写盘与写盘归因不挡在弹窗前。`outcome` 字段：取材结果：文本或失败语义。`settle` 字段：兜底轮收尾；AX 通道直读为 `None`。
  - `into_parts`：拆出产物与收尾：产物交通道上抛（弹窗链路启动），收尾由调用方在产物上抛之后调 `SelectionSettle::finish` 收口。
- `SelectionSettle`：兜底轮收尾的移交形态：`SelectionRead` 的产物被通道消费后，收尾以本类型独立存活到调用方收口。
  - `finish`：收口兜底轮：按读取时定下的决策恢复（或跳过）原剪贴板并置位写盘归因。在取材产物上抛之后、与读取同一事件线程上调用。
- `imp::CompositeReader`：选区读取的组合实现：AX 优先，读不到时先尝试激活宿主的无障碍树，仍拿不到再降级剪贴板兜底。激活器随读取器跨手势复用（会话内按 pid 去重并记忆唤醒常客）；取材轮次闩锁句柄传给兜底通道——写盘轮次由它置位，哨兵按计数归因消费。
  - `new`：创建组合读取器：传入与哨兵源共享的取材轮次闩锁句柄。
  - `read`：读取前台应用的选中文本。产物与收尾分离：`SelectionRead::outcome` 先行上抛（弹窗链路启动），兜底轮的恢复写盘经 `SelectionSettle::finish` 随后执行——恢复不挡在产物交付前。产物已修剪两端空白，纯空白选区按 `GlossError::SelectionEmpty` 报告。调用方保证：在平台事件线程上调用（收尾同线程）。唤醒常客判定在入口现读一次：常客与否随前台应用，一次读取期间不变；激活器的可变借用留给 wake 闭包。
