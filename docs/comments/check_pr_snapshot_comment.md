# check_pr_snapshot 决策记录

> 本文件随仓库跟踪（docs/comments/ 入库），改名与合并用 git mv 保留历史；文件内不留指向本文件的指针。

- 调用方：hooks.yml 的 content-snapshot 作业两步骤（写入与比对），事件参数只传
  拉取请求编号与头提交，取数、豁免解析、摘要配方与提交状态读写全部收口在本脚本，
  判罚口径不落第二处。
- 快照载体用提交状态而非工作流工件：工件按运行隔离，编辑事件触发的运行要读上一
  次运行的工件链路复杂且易断；提交状态挂着头提交，读写各一条命令，重复写入幂等。
- 摘要配方单点：SHA-256 覆盖标题 UTF-8 字节、单换行分隔符与正文 UTF-8 字节；正文
  空值在取数侧折算为空串（与评审结果门禁的取数同形）。写入与比对两侧共用同一配
  方函数，配方漂移即基线整体失效，不许第二处实现。
- 写入面覆盖开启、同步与重开三事件（工作流条件以「非编辑」承载）：开启与同步是
  计划明定的写入事件，同步重写必要——新推送换头提交后快照必须跟随，否则后续编
  辑比对不到基准；重开是兜底补充——拉取请求关闭期间推送换头提交不触发同步事件，
  重开时补写快照，堵住此后编辑因快照缺席而失败关闭的空窗。写入不按操作者排除：
  机器人开单与推送同样留下基线，此后人工编辑才有比对对象。
- 比对面（编辑事件）按操作者排除机器人，不按拉取请求（PR）作者：依赖机器人改写
  正文是常规操作，改写者可能是任何一个机器人账号；排除条件只放工作流一处，脚本
  不做第二份。作者为机器人的拉取请求不在排除之列——正文书写门禁按作者整体跳过
  是模板判定的取舍，快照比对没有模板语义，人工改写机器人拉取请求正文同样留痕。
- 豁免形态：正文首行以放行标记起头加缘由，反引号包裹与裸形态都认——裸形态过不
  了正文书写规则（外文字母进中文主体），认它只为让判罚清单指向正确的修复动作；
  标记在场而缘由缺席按通用缺缘由规则判罚、豁免无效，比对照常进行。标记锚定首行
  起始（可选反引号包裹加词边界）：首行中途提及（如把标记写进句子）与作更长标识
  符前缀都不构成豁免，防无意引用静默重写基线。
- 豁免的语义是重写基线而非永久免检：有效豁免在场即以当前版为基准重写快照，标记
  留在正文首行作审计痕迹；标记被移除后比对立即恢复——基线此时是豁免版哈希，移
  除标记的改写会再次红灯，锁在豁免后重新武装。旧基线不可考是计划风险节明示接受
  的弱点，强审计需豁免事件落评论存档，本阶段不做。
- 快照缺席与描述字段残缺都按无法完成判定（退出码三）失败关闭，绝不因没检查到而
  放行：修复指引指向写入事件（推送或重开即补写基线）。
- 已知边界（如实登记，不圆）：正文改写后若紧随一次推送，同步事件按当前正文重写
  基线，编辑红灯只留在检查历史与时间线里，不持久阻断合并——同步重写是计划明定
  的幂等语义，收紧它（同步时比对前一基线）超出本阶段范围；静默改写的即时红灯与
  历史留痕已覆盖计划验收面。头提交在分叉仓库的拉取请求上写状态会失败（状态接口
  只及本仓库提交），按基础设施失败关闭，本仓库分支模型下不出现。
- 仓库标识复用对账门禁的远端地址解析单点，不再写第二份。

## 与内容检查作业的分立（2026-10-31，收口计划阶段 5）

- 独立作业而非并入正文检查作业的三条理由：快照写状态需要提交状态写权限，正文检
  查保持纯只读，权限面按作业隔离；独立作业名进必需清单，管理员补设的动作有明确
  对象，对账门禁（阶段 1）随后按清单核对，缺设即报；机器人排除口径不同——正文
  检查按作者整体跳过，快照按操作者只排除编辑动作，同作业承载会把两套条件搅在一
  起。
- 作业形态相对计划字面属显式偏差，如实登记：计划 2.5 第 5 条的字面定案是
  「check_pr_prose.py 的 edited 作业前置调用」；本阶段任务指令在计划之外给了
  「与 check_pr_prose.py 的 edited 检查同作业或前置步骤，按仓库现状取舍」的自
  由度，本实现取分立独立作业——前置步骤形态拿不到独立检查名（必需清单没有明
  确对象）、拿不到权限隔离（写状态的权限摊给正文检查），且两作业的机器人排除
  口径不同，三条理由如上条。
