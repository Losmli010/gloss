## 替换策略：重命名交换（2026-11-07，Windows 移植 P3a）

- 运行中的可执行文件与已加载的动态库不可原位覆盖（文件锁），但改名不受锁限制——腾位走重命名交换：旧件改名加旧件后缀、新件就位、重启拉起新可执行文件，当前进程随后退出。旧件在成功后删除，若仍是本进程映像则删除失败、带痕迹保留（与系统（macOS）的 `.app.old` 保底同型），下一次更新腾位前清场自愈。
- 回滚与残留清理的语义定义在共享核心（`install_shared`），本文件只承载平台差异。

## 载荷结构：可执行文件加旁置文件（2026-11-07）

- 便携压缩包（zip）的载荷锚点是“与当前可执行文件同名的文件”：解包现场里按名定位，所在目录即载荷根，其下每个直接子项随行换装。锚定当前可执行文件名（而非固定名）使结构校验契约可跨平台测试，也不假设产物固定名。
- 发布打包（`package_zip.py`）只压可执行文件加旁置动态库（dll）进包根；压缩包带顶层目录的结构同样可定位（定位不假设层数）。

## 解压用压缩包（zip）库（2026-11-07）

- 系统（macOS）走系统自带 ditto，系统（Windows）没有等价的系统级命令行工具，进程内解压选压缩包（zip）库（工作区新依赖，Windows 目标节）：特形只开 deflate，与发布打包的压缩形态对齐，不开其余压缩格式。
- 解压的路径消毒（拒越界条目）与符号链接外逃防护由该库的解压入口承担；载荷定位只认普通文件（`file_type` 不跟随符号链接），恶意压缩包在结构校验一步落 `InvalidStructure`。

## 拉起：直接生成新进程（2026-11-07）

- 系统（macOS）经 `open` 走 LaunchServices；系统（Windows）直接生成新进程——父子无控制台耦合，当前进程随后的退出不影响已生成的新进程。生成成功即视为拉起完成，更深的启动验证（新进程存活）不在替换步承担。

## 错误镜像与 NotABundle（2026-11-07）

- 错误枚举与系统（macOS）实现同名镜像，共享流程（`update/mod.rs`）与设置页文案零改动编译。`NotABundle` 在本实现取值于 `current_exe` 失败——系统（Windows）无应用包概念，可执行文件所在目录即可替换位，不存在“不在应用包内”的常规路径。
