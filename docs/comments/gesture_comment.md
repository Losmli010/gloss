## 手势策略取舍

- 2026-09-19 取“拖拽释放”而不用其它方案的原因：双击会把“打开链接”这类普通操作误判成划词，修饰键确认需要额外的键盘全局钩子，停留判定需要定时器——拖拽释放是误触最少的最简状态机。其余策略（含框选 `RegionGesture`）待配置化与图像任务落地时引入。

## MIN_PRESS（最短按压时长 150ms，2026-09-30；2026-11-14 起随共享层单源）

- 起因：手势判定原本只有位移一条规则，HID 全局 tap 连拖 Gloss 自己窗口、
  以及各种瞬时甩动都会被判成划词（interaction_review 的 P2-11）。纯位移
  判据区分不了“有意的拖拽”与“按下后立刻释放的甩动”——两者位移都可以
  超过 12pt，差别只在按压时长。
- 取值缘由：人手有意的拖拽选择从按下到释放稳定在数百毫秒量级（一次普通
  点按的按压就有约 100ms，有意的拖拽还要加上拖动的时间）；而甩动/连滑类
  误触的按下与释放间隔趋近于零。150ms 落在两者之间、两侧都留足裕量——
  快甩滤得掉，最慢的正常点按与最快的拖拽都不受影响。不做成配置项：阈值
  是手感参数，暴露出去只会让用户调坏（与“手势开关不进设置”同一取舍，
  见“明确不做”）。
- 时间戳取事件自身的单调时刻而不是回调投递时刻：tap/钩子回调经运行循环
  或消息队列投递，同一手势的按下/释放两事件的投递延迟可以差一个节拍，拿
  投递时刻算时长会漂；事件自带时间戳则与投递节奏无关（系统（macOS）为
  `CGEvent` 纳秒时间戳、系统（Windows）为 `MSLLHOOKSTRUCT.time` 毫秒，
  换算成 `Duration` 的口径随平台回调）。2026-11-14 上移共享层后本常量
  （`MIN_PRESS`）与阈值、队列容量随共享模块单源；原系统（macOS）侧
  `MIN_PRESS_NANOS` 与系统（Windows）侧 `MIN_PRESS_MS` 的单位分叉随之
  消除。
- 注入式 live 测试相应在释放前真实 sleep 过时长下限（200ms）——注入事件
  自带真实时间戳，不睡就会被本条滤除，那是想要的行为。

## GestureDetector::feed（释放坐标载荷）

- 2026-09-20 手势判定从“是否触发”改为“触发 + 释放坐标”：释放事件自带坐标（事件自带坐标的既有口径，见 ButtonEvent 的模块注释），划词浮层跟随选区用的就是它。坐标整型化为 ScreenPoint（与 ScreenRect 同口径）在 platform→组装点边界完成，手势层保持 f64 原值判定阈值。
- 2026-11-14 坐标整型化随选区手势源端口实现一并住共享层（`poll` 直出
  `ScreenPoint`），不再有平台侧映射步骤。

## tap sink 的 panic 屏障与 release panic=abort（P2-1，2026-10-13）

- 为什么 release 上 `panic = "abort"` 后 sink 闭包里的 `catch_unwind` 保留而不删除：
  release 下屏障不再拦截，panic 在事发点 abort 进程（C 回调屏障的防 abort 保护
  同步消失——行为变更须在 PR 描述显式记录，开 PR 时落实）；dev/test 构建仍是 unwind（test 目标由 cargo
  强制 unwind），无屏障时 sink 的 panic 会穿过平台回调这个 C 回调边界
  直接 abort——屏障保的是开发构建的监听存活。删除只退化开发/测试构建的容错面，
  处置为旁注“生效边界”，与 events/mod.rs 的 `guarded` 同一口径。

## 符号契约（自代码注释迁入）

- `DRAG_THRESHOLD`：判定为拖拽所需的最小位移（系统逻辑点）：远高于点击抖动，又低于任何有意拖拽；坐标是逻辑点，不必按 DPI 折算。系统（Windows）侧坐标是物理像素（进程的每显示器（DPI）感知档影响取值），同一数值在不同缩放档的手感差异待真机校准（L4）。
- `ButtonEvent`：tap 层交给手势层的事件，坐标与时间戳都取自**该事件自身**。不能缓存“最近一次移动位置”：真实拖拽期间系统只投递拖拽事件而非移动事件，缓存会停在按下之前，释放时算出的位移恒为零，手势永远判不出来。时间戳同理取事件自带的（单调），按压时长不依赖回调投递延迟。`time` 字段：事件自身的时间戳换算为时长（`Duration`），粒度随平台（系统（macOS）纳秒、系统（Windows）毫秒）。
- `GestureDetector::feed`：无按下记录的释放（如监听启动前就按下的拖拽），静默忽略。
- `MouseSource::spawn_listening(create, run)`：共享侧启动入口：注入“事件创建”与“宿主运行”两个闭包，启动监听线程并**同步等待**创建相结果：成功返回手势源与降级标志，失败返回缺席源（原因已记日志）。创建相与阻塞相分离，失败在进宿主循环前就确定。创建相在回报前就消亡（panic 于纯 FFI 与装箱路径，理论不可达）：按缺失降级，与创建失败同一出口。降级标志只在宿主运行中途停止时置位，启动失败不经它表达。
- `spawn_tap`：启动 `gloss-mouse-tap` 监听线程（线程名两侧同口径）并同步等待创建相结果：成功返回事件通道（有界 256 格，容量单源），失败返回 `None`（原因已记日志）。
- `tap_loop`：监听线程的执行体：事件经 panic 屏障投递（满则丢弃），创建成功先回报，再进阻塞的宿主循环。平台回调是 C 回调，panic 穿过它直接 abort 进程：与事件线程的 guarded 同一纪律，unwind 构建下兜底后监听继续；release 以 `panic = "abort"` 构建时本屏障不再拦截，panic 在事发点 abort 进程（生效边界同 guarded）。兜底放在共享层而不在平台实现里，是共享形状与平台原语之间的分工——实现侧只需保证自己不 panic（它的活只是常量查表加读一次坐标与时刻）。panic 屏障：闭包的结果（含 panic 信号）有意整体丢弃，监听循环只关心是否继续。通道满时丢弃：手势判定不需要完整事件流，反压平台回调的代价远大于丢一次触发机会。创建成功先回报再进阻塞的宿主循环（回报通道只有一位且调用方正同步等待；即便对方已提前放弃也不影响监听）。此后只有“运行中停止投递”一条退出路径（监听无停止 API），置位降级标志并留 info 便于诊断。
- `Sink`（事件汇点）：创建相交给平台回调的入队闭包——平台回调把订阅到的事件翻译进 `ButtonEvent` 后只触汇点，回调自身不做手势判定也不直接触通道（架构速览“回调里只做事件搬运”）。
