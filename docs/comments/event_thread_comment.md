## 抽取缘由（2026-11-07，移植评审遗留 A1）

- 为什么立本模块：系统（macOS）与系统（Windows）的事件模块此前各持一份
  完全一致的平台无关形状（事件源契约、汇点、线程句柄、spawn、恐慌屏障、
  节拍抽干），无机器门禁锁同文，改一处漏一处会静默漂移；差异面只在运行
  循环宿主（运行循环（CFRunLoop）周期定时器对消息泵加线程队列定时器），
  抽取可行，选抽取而非同文校验门禁——共享代码从结构上消除重复，门禁只能
  在漂移后报警。
- 归宿：两平台的事件模块从本模块取共享形状并重新导出，消费方引用路径
  （`gloss_platform::events::…` 与装配契约的再导出）不变；本模块只在
  lib.rs 的模块声明上按目标门控（cfg 不进业务文件）。

## 符号契约（自两平台事件模块记录迁入）

- `EventSource`：组装点提供的闭包与命令处理器同等对待：panic 不允许带倒事件线程。
- `TICK_MS`：源事件的抽干周期（毫秒），两平台同值：运行循环无法阻塞等待 crossbeam 通道，只能按定时器抽干。手势到浮层的端到端延迟上界即此值；类型按各平台定时器接口自取（运行循环（CFRunLoop）取时长（Duration），消息泵取毫秒整数）。
- `EventSink`：事件线程的产物出口：④ 回传事件与 ① 平台事件，由组装点接上真实通道。`wake` 是主线程唤醒回调：主线程可能睡在事件循环里，发送成功后不叫醒它，消息要等下一个无关事件才被看到。发送失败（接收端已消失）不唤醒。
  - `new`：`events` 是 ④ 回传通道，`platform` 是 ① 平台事件通道；`wake` 只在发送成功后调用。
  - `send_event` / `send_platform`：主线程已退出时返回 `false`：消息丢弃，也不唤醒。
- `EventThread::join`：退出协议：调用方 drop 通道②的 Sender，线程抽干剩余命令后自行结束；`join` 返回即线程已终止。
- `spawn`：`on_command` 在事件线程上顺序消费通道②，`sources` 每个 tick 抽干一轮；两者都不允许把 panic 带进线程。运行循环经函数指针注入（各平台的 `spawn` 包装保持原公开签名）。线程缺失时应用仍能启动，但取材手势全部失效——必须留痕。
- `guarded`：应用代码注入的回调不允许把 panic 带进事件线程；捕获后循环继续服务。release 以 `panic = "abort"` 构建时 panic 在事发点直接 abort，`Err` 分支不可达——屏障只在 unwind 构建（dev/test 及其单测）生效。
- `tick`：一轮消费：先抽干通道②（出现 Disconnected 即退出信号），再抽干全部事件源——同一线程内命令总排在系统事件之前。`send_platform` 成功时经 `notify()` 调组装点注入的唤醒回调。
