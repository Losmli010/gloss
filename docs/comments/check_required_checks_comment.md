## 脚本存在的原因

- 2026-10-31 门禁收口计划（docs/plans/gate-process-closure-plan.md）阶段 1：脚本合入与分支保护配置是两个无对账的动作（PR #273 双红灯照合、#274 配置动作晚于代码合入），必需检查清单缺了 Review result check 无人发现。本脚本把「工作流里应然会跑的作业」与「托管平台实际设的必需检查」做成差集对账，缺漏带规则标识与修复指引打印，配置动作由管理员在托管平台完成。

## PR 链路事件的口径

- 2026-10-31 对账面取 pull_request、pull_request_target、pull_request_review 三个事件：检查运行挂在这些事件产出的运行上、落在 PR 头提交，红灯能挡合并（闸门语义）；push、schedule、workflow_dispatch 等不挂 PR，对账无意义。计划文档写作「pull_request 事件下会运行的作业」，但阶段 1 的验收（恰好报 Review result check 缺失）要求评审事件作业进对账面——评审作业挂在 PR 头提交、同样能设必需，故三事件并集才是「应然」全集；作业条件把某个事件排除在外时只从该事件收集（如评审作业之于 PR 事件）。
- 2026-10-31 工作流声明了 PR 链路事件才参与对账：schedule 与 workflow_dispatch 独享的工作流（stale、security-audit、eval、perf、release）整体不收，否则定时作业全成误报。
- 2026-10-31 收口计划阶段 3 补进 pull_request_review_comment：行内评论事件与评审事件同性质——检查运行挂在 PR 头提交、能设必需，不进收集面即成静默漏报的洞（宁误报不漏报）；收集面扩后，红牌定位的评论检查作业按显式豁免放行（见豁免登记节），对账不把它报为缺必需。

## 条件求值的三值逻辑

- 2026-10-31 作业级 if 求值只认子集：事件名比较、布尔连接、取反、括号与 endsWith、startsWith、contains；github.event_name 以合成事件名代入，其余上下文路径（评审正文、作者名等）静态不可知，按未知处置。三值逻辑与 GitHub 求值语义对齐：假与未知相与为假（pr-template 之于评审事件正确排除），真与未知相与为未知、未知按会运行收集（review-result 之于评审事件正确收集）——宁误报不漏报。
- 2026-10-31 条件解析失败同样按会运行处置：误报可见、可走豁免登记，静默漏报不可见。步骤级 if（如 always()）不影响作业是否运行，不参与求值。
- 2026-10-31 拉取请求的 types 过滤不参与判定：types 收窄（如只留 labeled）属未来形态，漏收的代价（漏报）高于多收（误报），按声明即收处理。

## 工作流子集解析器（不引 YAML 依赖）

- 2026-10-31 门禁脚本零第三方依赖是仓库现状（持续集成只装 pytest 与纯文本工具，无 PyYAML），为对账引入依赖会改变 CI 装机面；故按仓库现行九个工作流的形态写行级子集解析器：顶层 on 与 jobs 两键、子键映射、流式清单、折行块标量（条件跨行接回一行）、作业级 name 与 if；steps 与 strategy 等子树整段跳过，只认作业直接子键的精确缩进，防止把步骤名误当作业名。
- 2026-10-31 解析失败按无法完成判定退出码三（INFRA），绝不猜：解析器覆盖不到的未来形态当场红出来，比静默漏收安全；修复动作是扩子集或登记豁免，都有痕迹。
- 2026-10-31 评审补强：on: 的内联标量与流式清单元素按事件名形态（标识符字符集）准入校验——此前 {pull_request: null} 这类流式映射会被当成伪事件名，整份工作流静默退出对账面（既不报错也不进应然集合，属静默漏报）；现在子集之外的形态一律解析失败红出来，兄弟洞（流式清单内嵌映射）同批封住，on: 子键块形态本就经键行校验红出来。
- 2026-10-31 作业显示名保持字面（含矩阵展开表达式），检查名与必需 contexts 的匹配是字面全等；显示名含表达式时静态对不了账，走豁免登记。

## 豁免登记

- 2026-10-31 豁免住在脚本常量区（EXEMPTED_JOBS，显示名到缘由），不在配置文件：豁免是对账语义的一部分，随脚本评审。登记项与收集面互相对照，登记了却收集不到的陈旧条目也打印提醒。现登记两条：Build 的矩阵展开名——必需清单里是展开后的 Build (aarch64-apple-darwin)，静态对账只能看到表达式字面，展开名与必需清单的一致性由人工核对（豁免缘由里写明展开名，供核对锚定）；Review comment check——行内评论检查按收口计划阶段 3 定位红牌，运行且红灯但不阻断合并，豁免缘由写明定位出处，对账只对应进闸门的作业判罚。
- 2026-10-31 已知边界：若管理员把展开名从必需清单摘除，豁免使对账仍绿，反向漂移（必需多了、应然少了）按计划不判罚，本脚本不做反向对账。
- 2026-10-31 红牌豁免的生效前提是作业先被收集进对账面（评论事件在收集面内）：豁免登记约束「收集到但不进闸门」，收集不到走的是陈旧条目提醒——两条路径不能混，否则红牌作业换个工作流文件就绕开登记。

## 接口取数与仓库标识

- 2026-10-31 必需 contexts 经 gh api repos/{owner}/{repo}/branches/{branch}/protection 取全量载荷后在本脚本解析（required_status_checks.contexts），不用 --jq：解析层可单测打桩，gh 只当传输。gh 失败（含权限不足）按无法完成判定退出码三，指引写明令牌需要管理面只读授权。
- 2026-10-31 仓库标识解析自 origin 远端地址（https 与 ssh 两形态），走统一版本库出口；分支名钉死 main——对账对象是合并目标分支的保护配置。
- 2026-10-31 持续集成侧由 hooks.yml 的 required-checks-reconcile 作业承载，作业以 push 条件只在主分支推送后运行——对账作业自身若随 PR 跑，会把自己的检查名收集进应然集合，与必需清单形成自指，且首个 PR 上必然自报缺失。
- 2026-10-31 计划设想的「作业级 administration:read」在现有工作流语法下不可声明：GITHUB_TOKEN 的工作流权限作用域没有管理面，声明即整份工作流解析失败（实测：推送后 Hooks 运行以文件路径为名、零日志失败，九个作业全部停摆）。凭据改走仓库密钥（REQUIRED_CHECKS_TOKEN，管理员配细粒度令牌只授管理面只读），密钥缺席时作业按无法完成判定红灯——不静默放行，红灯即「CI 侧对账未就绪」的可见信号。
