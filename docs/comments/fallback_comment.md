## read_with（一轮兜底读取装配）

- 流程（两侧逐字同构后单源）：快照原剪贴板 → 注入复制快捷键 → 轮询确认目标应用写入 → 读回 → 读回成功且现值未变才按快照恢复；未确认时重注入一轮再等一个完整超时窗口。整条流程运行在平台事件线程（调用方保证亲和性），恢复操作同线程执行。
- 失败轮一律不恢复（2026-10-15，评审修订为三态）：失败意味着写入未确认或读不出文本，板上三态皆不覆盖——未变（无需恢复）、本轮之外的新写入（目标应用迟到的复制、用户的复制）、注入副产物（确认了写入却读不出文本——前台选中的可能是图）。第三态留在板上并按外来写入放行：它正是前台应用对注入复制键的响应，是图即触发图片解释，好过静默清掉。旧实现无条件恢复会把用户的图清掉。
- 成功轮保留 `current_is_ours` 守卫：只有现值仍是自身读回的文本才恢复，板被再次改动即视为他人内容——用户窗口期里可能自己复制了新内容，无条件恢复会把用户的新拷贝清掉。校验用文本读取比对，不另做变更探测。
- 归因口径（2026-10-15 收口）：自报写盘数只计可归因的写入——文本读回成功（`Ok` 蕴含写入确认）计 1，恢复执行按实际写盘数计；“确认了写入却读不出文本”无法与轮次内外来复制区分，一律记外来（自报 0），由哨兵的计数归因放行、有图兜底判定。
- 归因起点先于快照：快照要拷贝内容字节（大图数十毫秒），归因基线若在快照后读取，其间落进的外来写入会被算进本轮自身写盘的基线吞掉；先于快照读取则该窗口内外来写入照常放行。
- 快照放弃即整轮空闲：结构读不出或内容无法如实保全时整体放弃（快照返回空），此刻尚未注入、板未被触碰——无恢复收尾亦无写盘归因。放弃边界随快照内容类型留在平台侧，以各侧快照模块文档为准。
- 确认窗改参数注入（2026-11-17）：确认超时随 `read_with` 参数进入，绑定侧传共享常量——替身测试零延时驱动全部路径（同步点用替身应答不用时间），与 `restore_with_retry` 的退避参数注入同款（退避经参数注入以便单测零延时驱动的既有先例）。
- 快照缝先读板文本作入参（2026-11-17）：快照闭包收到的首参是注入前的板文本读取结果——系统（Windows）的快照判定本就以它为入参（纯函数三入参形态），系统（macOS）的快照不读文本、结果原样弃置。系统（macOS）侧因此多一次只读的板文本读取（读不改板、不推进代数、不落日志），观察差异为零。

## FallbackSettle（恢复收尾）

- 产物与收尾分离：恢复决策与写盘归因装在收尾结构里，调用方在取材产物上抛之后 `finish`——恢复写盘（大板数十至数百毫秒）不再挡在弹窗前。归因语义：`enter` 在恢复之后置位（自报 = 确认的注入复制 + 恢复写盘数），哨兵消费时序（事件源只在命令抽干后轮询）不受移位影响。
- 恢复收口用 Drop 守卫而不是在各退出点手工恢复：`read` 的退出路径有快照失败早退、监视失败、注入失败、确认超时、读取成功、读取失败、panic 展开等多种，手工收口漏掉任何一条都会把选区滞留在用户剪贴板里；Drop 让“未显式跳过即恢复”成为默认语义，panic 展开也覆盖。被否备选：在外层包一层统一恢复——一样要靠人记得每条新退出路径都穿过它，守卫的默认语义更硬。
- `pending` 为空即本轮未注入（板未被触碰），收口无事可做、不进写盘归因。
- 自报写盘数 = 确认的注入复制计数（0/1）加恢复实际写盘数；`restores_on_unwind` 观察器（2026-10-30 起）供测试区分“放弃轮（无恢复契约）”与“契约轮”，公开契约观察而非摸内部状态。

## PendingRestore

- 待执行的恢复：持有快照与还原函数指针（还原函数由绑定侧提供——恢复语义与失败留痕随快照内容类型留在平台侧）；受控路径经 `restore_now`（恢复、留痕并返回实际写盘数）或 `skip_restore` 显式收口，panic 展开由 Drop 兜底按快照恢复。
- `skip` 只由收口路径显式置位，构造即武装 Drop 兜底；恢复失败已由还原函数内部留错误痕（环节与状态码），不恐慌不上抛、不影响调用方的主结果。

## wait_for_write（写入确认轮询）

- 纯时序函数：给定基线、探针与截止时间，轮询到代数前进或超时；探针返回空（本轮读数失败）继续等，与基线不同即认为目标应用已完成写入；到截止仍未变化返回否，调用方据此走失败路径。轮询先于截止检查——每窗至少探一轮。

## attempt（注入与确认）

- 首发注入未确认时重注入一轮、再等一个完整超时窗口：实测进程启动后的第一发常被系统吞掉，前台应用繁忙时也会漏收，而注入调用本身返回成功——不重试的话这批划词兜底整批失败。此刻选区仍原样在目标应用里，重注入没有副作用，换来兜底可靠性；代价是最坏两倍确认窗占住平台事件线程，期间其余命令与事件排队（事件源侧缓冲），由调用方处理在途重复触发。注入失败即弃、不重注入——失败与未确认是两个判据。
- 读回轮询：读到非空文本即成功；读到空或读失败不等于失败，继续轮询到 deadline 再收口——目标应用清板后写入是异步序列，半写入间隙读空是常态。
- 确认窗口收紧（2026-10-16）：兜底是取材末段通道，窗口只约束无响应宿主上的最坏路径（两轮最坏 1.6 秒）；常规确认数十毫秒内完成。7 天日志中兜底轮 0 次触发到超时，收紧不损判定率。

## restore_with_retry（恢复重试骨架）

- 单次恢复序列失败短退避后重试、成功即止：剪贴板服务出现百毫秒级的持续不可用时短窗口熬不过去（剂量沿革见下），且只在已失败路径上付出。写盘数累加全部尝试的实际写盘数（含失败尝试）；耗尽保留末次失败环节与状态码，供统一错误出口回放定位。
- 结果形状随骨架单源为泛型（2026-11-17）：`RestoreOutcome` 携带成败、实际写盘数、失败环节与系统状态码；环节枚举（系统（macOS）的开板、预建、清板、写入与系统（Windows）的句柄、写、放、清）与系统状态码语义留在平台侧。无系统状态码的场合记 0（系统（Windows）的恢复路径均无状态码）；系统（macOS）名称构造失败记 -1。
- 成功收口的环节重置为平台环节枚举的默认值（成功形态），状态码清零。
- 剂量沿革（自两侧平台记录合并）：初版无重试，持续集成（CI）高负载虚拟机偶发失败暴露瞬时失败面；3×50ms 被证伪（插桩更高负载下三次尝试未成功清板一次，故障窗口不小于整个重试跨度）；现行 6×200ms——预算上限对齐事件线程既有最坏占用（写入确认两轮 1.6 秒）的一半，失败环节与状态码进 error! 日志，live 测试经统一日志出口取同一条进断言消息；若未来再度失败，断言消息可直接定位环节与状态码，据此再定剂量，不盲调。系统（Windows）恢复的写盘数按剪贴板序列号真实跳变数自报（清板一次加每个放回的风格各一次），少报会让恢复回板的图被判成外来复制、伪触发图片任务（反向替身测试钉住，见剪贴板监视记录）。

## 已知残差（2026-10-15，二轮评审归档；自系统（macOS）记录迁入）

- 失败轮的注入副产物若既非图片也非可读文本（仅富文本风格、空文本写入等窄场景）：不恢复、不触发，用户原剪贴板被静默替换。这是“只读元数据”归因的不可约残差（内容指纹方案因“允许粘贴”授权红线被否）；主场景（图片副产物）已由外来放行 + 有图兜底消解。

## 板面原语束（FallbackBoard）与监视缝协议

- 原语以结构体束注入（2026-11-17）：一轮读取需要六个平台缝（基线计数、快照、还原、监视、注入、文本读取），散参会超参数判罚上限——沿用组合通道让渡节奏束（`Pacing`）的束形态，板面原语束 `FallbackBoard` 一次注入；还原是函数指针（非泛型闭包），供恢复收尾在析构时调用。
- 监视缝协议（2026-11-17）：注入前首调返回确认基线，此后每调返回代数现值，读不出返回空、继续轮询。首调给基线把“建立监视”与“读基线”合成一个缝调用，免去为探针单设泛型参数；基线必在注入之前确立（系统（Windows）的序列号基线、系统（macOS）的恒零基线都取自监视建立时）。两侧代数语义见各自绑定记录：系统（macOS）用同步标志闩锁（只能回答“变没变”），系统（Windows）用剪贴板序列号差（系统级单调计数）。

## 注入实现从 rdev 换为手写 FFI（2026-10-13，沿革指针）

- 缘由与复刻依据见 event 记录；行为保持逐字一致，错误路径的“失败即弃 + 配对补发释放”保留，写入确认窗口是成败的最终判据。授权语义不变：注入助手返回成功只代表事件构造成功，未授权时事件被系统静默丢弃，成败由写入确认窗口分辨。
