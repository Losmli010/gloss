# check_review_comment.py 注释记录

- 调用方：hooks.yml 的 review-comment 作业（pull_request_review_comment 的
  created 与 edited 事件，正文取自托管平台接口）。客户端钩子不路由行内评论：
  行内评论只产生在托管平台的评审界面上，本地钩子的触发面（提交、建链改链、
  评审提交）覆盖不到它，不做够不到的判定。
- 判定面只有书写规则一项：单条评论没有模板骨架，小节与声明判定不套——骨架
  与声明的意图是约束正式产物（正文模板声明、评审结果），评论是交流载体，全
  套会误伤；书写规则复用语言规范库的标记语言遍历，与拉取请求正文同一口径，
  直角引号、英文整句与裸代码引用在评论里与正文同判。
- 标识沿用登记表内的书写规则标识，不另设：判罚消息经统一诊断出口打印，标识
  的含义与豁免方式以登记表为准；与评审结果门禁的取法一致（照实透传），与拉
  取请求内容门禁的改标做法（硬违规统一改挂本域标识）不同——改标是为了让多判
  罚域共用一个域标识，本门禁单域单面，透传即可定位。
- 机器人评论与空评论的排除只放钩子工作流的作业条件一处，本脚本不做第二份排
  除判定：排除是"没有可判定产物就不开判定"的编排事实，住调用方；空正文进判
  定面即无违规放行，不设空正文规则——与评审结果门禁的空正文判罚相反，那里空
  正文意味着正式产物缺席，这里空评论只是没有评论，没有可补写的产物。
- 作业定位红牌：不进必需检查清单，红灯靠人看到后修复，不拦合并（初版曾在阶段 1
  对账门禁的豁免清单登记，该门禁回退后豁免登记随之消失，红牌定位不变）。
- 软约束候选分流与评审结果门禁同款：书写规则条目原样透传，候选按警告通道打
  印、不计违规与退出码；运行函数只回硬违规。
