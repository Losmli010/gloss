## 模块（为什么是纯启发式、为什么无条件）

- 2026-09-24 任务 14 的既有两个面：**场景闸门**（发不发这条内容）与**内容
  闸门**（这条内容发不发得出去）。两者都实现成纯函数放 core：判定是“给定
  事实算什么”，与“怎么读到事实”（NSWorkspace / Carbon）、“怎么拦下发”
  （通道③）无关，因此不需要 IO、不需要替身即可全矩阵驱动。
- **两道闸门都不出浮层、都没有旁路出口**（2026-09-24 修订，见 config_comment.md
  的“防护字段的移除”）：场景闸门让触发不发生，内容闸门让取材产物止步于
  状态机，各自只留一行 warn。初版曾把内容闸门做成“确认卡 + 仍要翻译”，
  被否掉的理由是**它把判断权又交回给了用户**：确认卡是弹窗，弹窗是用户会
  条件反射点掉的东西，而命中恰恰发生在用户没意识到自己在选凭据的时候。
  安全不交由用户控制——闸门关不掉，也就没有“手滑放行”这条路。
- 为什么不做“正则表达式库”而是手写扫描：唯一需要调库的是熵与 Luhn，前者
  是一遍字符统计、后者是十行算术；引一个正则引擎只为几条前缀匹配，会把
  core 的依赖面扩大一圈，且正则的匹配语义比“前缀 + 长度下限”更难在评审
  时一眼看穿。宁可多写二十行、判定完全可读。
- **误报的代价与漏报的代价不对称**：漏报 = 密钥进了网络（不可逆）；误报 =
  这段文本这次发不出去（用户改一改再划，或换一处划）。所以阈值一律往“宁可
  少报”调，但**不是**毫无节制——判据里每一条都要能对着一段真实文本说清
  “它为什么算”，否则用户会在正常文本上被反复挡住，而这一次他没有开关可
  以关（闸门对用户不可见）。这就是 `ordinary_text_is_never_flagged` 与
  `prose_about_tokens_is_not_a_hit` 两条测试存在的理由：它们钉的是**误报**，
  不是漏报。

## trigger_block / matched_entry

- 名单是内建常量 `SENSITIVE_APPS`（七条 bundle id：密码管理器与钥匙串访问），
  入参只有场景事实——没有开关可判，闸门恒定生效。
- 安全输入的优先级高于应用名单：两路因由是不同的日志行，先报谁要从“哪条更
  不依赖其他事实”定——安全输入态与前台是谁无关，先判它才不会因为拿不到
  前台应用而漏掉。
- `matched_entry` 返回**命中的名单条目**而不是 `bool`：日志要把那一行回显出来
  （“谁拦的”比“拦了”有用）。名单条目与前台应用的 bundle id 或本地化应用名
  逐字比对（ASCII 大小写不敏感）：bundle id 是跨语言稳定的标识，名字那一侧是
  名单可编辑时代的遗留——内建名单因此全用 bundle id，名字路径实际不会命中，
  留着是因为 `FrontApp` 本来就带着它、去掉反而要多改一处平台取值。
- 前台应用取不到（无图形会话）时按“无事实”放行：探针读不到东西不该升级成
  拦截，否则一次 NSWorkspace 抖动就会让划词整体失灵。
- 源码注释迁入——`trigger_block`：触发前的场景闸门，`None` 即放行，`Some` 即不取材不触发。判定顺序与两个事实无关，只为“先判不依赖前台应用的那条”。`matched_entry`：名单匹配，Bundle ID 或应用名与 `SENSITIVE_APPS` 的条目逐字相等（ASCII 大小写不敏感）即命中，返回名单里那一条（名单目前全是 bundle id）。

## 2026-09-26 评审整改：判据面与写明的取舍

- **前缀边界按 ASCII 判**（`is_ascii_alphanumeric`，不是 Unicode 的
  `is_alphanumeric`）：汉字属于 Unicode Alphabetic，用后者时 `密钥是sk-…`
  这种**没留空格的中文正文**里贴着的令牌整片漏掉（前缀位置被判成“词内”）。
  中文书写不靠空格，这一条对中文产品是硬要求；换成 ASCII 判定后
  `disk-space-2024` / `risk-managed-portfolio` 仍不中（它们的 `sk-` 前面是
  ASCII 字母）。判据：改回 Unicode 版，`tokens_embedded_in_structured_text_are_detected`
  里的两条中文紧贴样例即红。
- **长档不看形状是写明的取舍**：≥16 字符的前缀主体一律算令牌，因此
  `sk-learn-scikit-learn`（18）这类长复合词会中，而 13 字符的同款不中。
  取舍的理由是长档的误报面（`sk-` 开头的长英文复合词）比漏报面（手写的长
  假密钥）窄得多；`the_long_tier_of_prefixed_bodies_ignores_shape` 把这条
  边界钉在明面上，改判据时它会红。
- **卡号在组分界处也判一次**：`4111 1111 1111 1111 12/26`“卡号 + 有效期”
  是最常见的粘贴形态，只在末尾判会把后段数字并进累加串、整条漏掉；连续
  分隔符（`4111  1111  1111  1111`）同理。代价是误报面变宽：**每个落在
  13–19 位窗口内的分界各给一次 1/10 的机会**（实测 `1234 5678 9012 37 456`
  会中——它的 14 位前缀恰好过 Luhn），分组越多的长数字串累计概率越高，比
  “只在末尾判一次”不再同阶；换来的是“卡号 + 有效期/CVC”这种最常见的
  粘贴形态不漏，取舍按漏报优先定。
- **AKIA 只看连续的大写字母与数字**（`aws_body_run`，与其余前缀共用的宽
  主体字符集分开）：`AKIA…EXAMPLE=` 的 base64 填充符、`AKIA…+1` 的后缀属于
  下一个词元，不该让编号作废；反过来 `AKIAABCDEFGH-IJKLMNOP` 这种带连字符
  的伪编号不算（真编号没有连字符）。
- **场景闸门与内容闸门对“上一次的卡片”处理不同，这是有意的**：内容闸门
  拦下的是用户**已经表达意图**的一次取材，屏上留着的旧卡片会被读成“这次
  划词的结果”，所以收起它；场景闸门拦下的是“这次手势根本没发生”（密码
  框聚焦、敏感应用内），不动屏上任何东西。

## detect_sensitive 的判据与顺序

- 顺序是**确定度降序**：私钥块 → 令牌 → 卡号 → 高熵串。同一个字符串可能
  同时满足多条（私钥块里也有 `sk-` 形态的行、卡号也符合高熵），返回更确定
  的那一类，用户读到的因由才不是“像是随机凭据”（最含糊的一条）。
- `has_private_key_block` 判的是“含 `-----BEGIN` 且含 `PRIVATE KEY`”而不是
  完整 PEM 头：`.pem` 文件里私钥与证书块共存，用户选中的片段未必从头开始。
- 令牌类的长度下限是**两档**（`MIN_TOKEN_BODY` 16 / `SHORT_TOKEN_BODY` 4）：
  长过 16 一律算令牌；4–15 只在主体含数字或大写时才算。分档的缘由是 2026-09-26
  owner 真机报障“前台选中含 `sk-` 的假密钥没有拦截成功”——复核日志后确认
  取材链路正常（`InputReady` 拿到的就是选区原文），是**判据太窄**：单手写的
  假密钥（`sk-123456`、`sk-abc123`）全在旧下限之下，被当成“散文”放行了。
  短档要求“含数字或大写”是为了挡住 `sk-learn-scikit` 这类普通小写复合词，
  同时留住 `sk-abc123`。代价照旧：全小写无数字的短串（`sk-abcdefgh`）不命中，
  它与普通小写复合词在纯形状上不可分，只能靠猜哪边代价更小——这次选了漏报。
- 前缀判定看的是“**前缀前面不是 ASCII 字母数字**”，不是词首（`is_prefixed_token`
  在词内扫描）：`{"key":"sk-xxx"}`、`?token=sk-xxx`、`/sk-xxx`、`“sk-xxx”`
  这些形态里前缀前面是 `"` `=` `/` `“`，旧版按词首比对**整片漏掉**；反过来
  `disk-space-2024`、`risk-managed-portfolio` 里的 `sk-` 前面是字母，照样不中。
  这是“用户实际会选中的样子”在结构化文本里最常见的两种：JSON 与 URL。
- 主体取的是**紧跟前缀的那一段连续本体字符**（`body_run`），不是词尾：
  `"sk-abc123"` 的收尾引号、`sk-abc123}` 的右花括号不该让前面的令牌作废。
  本体字符集在前缀这一支放宽到标准 base64（`+` `/` `=`）——手写的假密钥常带
  它们；`Bearer` 与高熵两支仍用窄字符集，那两支没有前缀这个强信号托底。
- `INVISIBLE` 在判定前从**副本**里剥掉（零宽空格/连接符、词连接符、BOM、
  软连字符）：网页与编辑器复制会把它们塞进令牌中间，把前缀或主体切断；
  发送的原文不动，剥的只是判定输入。只在真含有它们时才拷贝。
- `AKIA` 单独一条（而不是并入前缀表）：AWS 的 access key id 不带分隔符，
  且它自己的字符集（大写字母与数字）与前缀表其余项不同。
- 卡号走 Luhn 且要求**至少两个不同数字**：全零串过 Luhn，若不排除，
  `0000 0000 0000 0000` 这种明显不是卡号的东西（或一串补位零）会天天弹卡。
- 高熵判据是三个条件的**合取**：长度 ≥ `ENTROPY_MIN_LEN`、字符集限于
  base64url 类、三类字符（大写/小写/数字）齐备、且 Shannon 熵 ≥
  `ENTROPY_MIN_BITS`。少任何一条都会误报：`a_very_long_snake_case_identifier`
  有三类字符但熵不够，一段中文有熵但没有三类字符，`aB3xK9` 三类齐备但太短。
- `TRIMMED` 剥掉包裹标点：用户选中的常常是 `sk-xxx`（带引号或反引号）或句中
  的 `Bearer eyJ...`，不剥则前缀判定在两端被标点挡住。
- `after_assignment` 按**最后一个等号**切出取值半边，现在只剩 `Bearer` 那一支
  在用：前缀那一支改按“前面不是字母数字”判之后，`.env` 行
  （`OPENAI_API_KEY=sk-...`）与 shell 导出语句（`export GITHUB_TOKEN=ghp_...`）
  天然命中，不需要先切等号了（这条当初是 `token_prefixes_are_detected` 在门禁
  里真的红过一次才补上的，漏的是最常见的那一类）。`Bearer` 是双词形态，
  `AUTH=Bearer eyJ...` 里那个等号仍要切掉，所以它留着。
- 源码注释迁入——`after_assignment` 是赋值形态（`AUTH=Bearer ...`）的取值半边：切**最后一个**等号，`Bearer` 的前面可能是 `AUTH=`，取最后一个更稳。

## SENSITIVE_APPS

- 触发被场景闸门拦下的前台应用名单：密码管理器与钥匙串访问——这些应用里的划词几乎只会是凭据（主密码、生成的口令）。
- 内建常量而非配置项：名单一旦可被编辑，防护就有了旁路出口。匹配对象是前台应用的 Bundle ID 或应用名（不区分 ASCII 大小写），见 `matched_entry`。

## FrontApp

- 前台应用标识：敏感应用名单的匹配对象。
- `bundle_id`：`CFBundleIdentifier`，如 `com.1password.1password`；`name`：面向用户的本地化应用名。
- `is_self`：前台应用是否 Gloss 自身进程（探针按 `processIdentifier == getpid()` 判定）。防误触用：连拖 Gloss 自己的浮层不该触发划词；名单匹配不消费它。

## SceneFacts

- 触发前的场景事实：壳在取材前取一次，交状态机判定。
- `secure_input`：系统是否处于安全输入态（密码框聚焦）。
- `front_app`：前台应用；探针取不到时为 `None`，闸门按“无事实”放行。

## TriggerBlock

- 触发被场景闸门拦下的原因：只记类别与命中的名单条目，不含选区内容。
- `SecureInput`：安全输入态（密码框聚焦）；`BlockedApp`：前台应用命中敏感应用名单，携带命中的名单条目（原样，供日志对照）。

## SensitiveKind

- 内容命中的敏感信息类别。类别进日志，命中的原文不进。
- `Token`：已知前缀的密钥/令牌（`sk-`、`ghp_`、`AKIA`…）或 `Bearer` 后接长令牌；`PrivateKey`：PEM 私钥块；`HighEntropy`：高熵长随机串；`CardNumber`：通过 Luhn 校验的银行卡号。

## detect_sensitive（源码注释迁入）

- 发送前的内容闸门：命中返回类别，未命中返回 `None`。
- 只做高置信度模式，判定顺序与命中概率无关，只为“更确定的类别先报”：私钥块 → 密钥/令牌 → 卡号 → 高熵串（前者命中就不再往下猜）。
- 不可见字符剥离放在最前：网页与编辑器复制时常把不可见字符混进令牌中间，前面的词首判定会被它挡住。只在真含有它们时才拷贝副本（选区是热路径）。

## 判据常量（源码注释迁入）

- `TRIMMED`：词两端剥掉的标点——密钥常贴着引号、括号、markdown 强调符被复制走；末三个依序是中文句号、逗号、顿号（`\u` 转义与 `INVISIBLE` 同构）。
- `INVISIBLE`：复制时会切断令牌的不可见字符——零宽空格/连接符、词连接符、BOM、软连字符。
- `TOKEN_PREFIXES`：已知密钥/令牌前缀（逐字匹配，大小写敏感——这些前缀本身区分大小写）；`sk_live_` / `sk_test_` 是 Stripe 的两档 secret key，`sk-proj-` 那一类已被 `sk-` 覆盖。
- `MIN_TOKEN_BODY`：前缀之后算令牌的主体长度上限档，长过它一律算令牌。
- `SHORT_TOKEN_BODY`：短主体档的下限——手写的假密钥（`sk-123456`、`sk-abc123`）就在这一档，长度够了还得**含数字或大写**，普通小写复合词（`sk-learn-scikit`）不能中。
- `MIN_BEARER_BODY`：`Bearer` 之后的最小令牌长度。
- `AWS_KEY_ID_BODY`：AWS access key id 的主体长度（`AKIA` 后 16 位）。
- `ENTROPY_MIN_LEN` / `ENTROPY_MIN_BITS`：高熵串的最小长度与最小香农熵（bit/字符）。
- `MIN_CARD_DIGITS` / `MAX_CARD_DIGITS`：卡号的位数区间（ISO/IEC 7812 的现行区间）。

## has_private_key_block

- PEM 私钥块：`-----BEGIN` 与 `PRIVATE KEY` 同现即算（`RSA`/`EC`/`OPENSSH`/`PGP … BLOCK` 各变体都含这两段，不必逐个枚举）。

## has_token

- 密钥/令牌：按空白切词逐词扫描前缀，同时盯住“前一个词是 `Bearer`”这一双词形态——一趟遍历里两件事一起做，不为此把整段选区收成 `Vec`。

## is_bearer_token

- `Bearer <token>`：前一个词是 `Bearer`（大小写不敏感，允许 `AUTH=Bearer` 这种赋值形态）且当前词够长。

## is_prefixed_token

- 词内扫描已知前缀与 `AKIA`：命中要求前缀**前面不是 ASCII 字母数字**（词首，或前面是 `=` `:` `"` `/` 这类分隔符）——`{"key":"sk-xxx"}`、`key=sk-xxx`、`密钥是sk-xxx`、`/sk-xxx` 因此都能命中，而英文复合词（`disk-space-2024`、`risk-managed-portfolio`）不会。

## is_prefixed_body / body_run / is_prefixed_body_char

- `is_prefixed_body`：前缀令牌的主体形状，两档长度（见 `MIN_TOKEN_BODY` / `SHORT_TOKEN_BODY`）。
- `body_run`：前缀之后连续的主体字符，遇到别的字符即止——`"sk-abc123"` 的收尾引号、`sk-abc123}` 的右花括号不该让前面的令牌作废。
- `is_prefixed_body_char`：前缀令牌的主体字符集——URL-safe 与标准 base64 都在内（`+` `/` `=` 常见于手写的假密钥，`Bearer` 与高熵那两条仍用窄字符集）。

## aws_body_run

- `AKIA` 之后连续的 access key id 字符（大写字母与数字）：`AKIA…EXAMPLE=`、`AKIA…EXAMPLE+1` 里的填充符与后缀属于下一个词元，不该让编号作废——判据只要求“够长的一串大写字母与数字”。

## is_token_body

- 令牌主体：长度够且字符全在 `[A-Za-z0-9._-]` 内（URL-safe base64、十六进制、JWT 段都在此列）。

## has_high_entropy_token

- 高熵长随机串：单个无空白长词、字符全在 `[A-Za-z0-9._-]` 内、长度 ≥ 32、小写/大写/数字三类字符齐全、香农熵 ≥ 4.5 bit/字符。
- “三类字符齐全”是排除伪阳性的主力：长标识符（全小写加下划线）、路径（含 `/`）、中文长句（非 ASCII）都过不了它。命中即拦截、没有旁路出口，所以这里宁可漏报：漏报只是这一次照常发送，误报却会让用户彻底失去这条路径的可用性。

## shannon_bits_per_char

- 香农熵（bit/字符）：字符分布的均匀度。随机串显著高于自然语言与命名，是“像不像随机生成”的量化判据。

## has_card_number

- 卡号：13–19 位数字（组间允许空格或连字符连续出现）、过 Luhn 校验、且至少出现两种不同数字（全同数字串是填充号，不是卡号）。
- 判定点有两类：**每个组分界**与**整段末尾**。“卡号 + 有效期/CVC”是粘贴卡片信息最常见的形态，只在末尾判会让 `4111 1111 1111 1111 12/26` 这类因为后段数字并进累加串而整条漏掉；组界处提前判一次就看得见那 16 位。

## luhn_ok

- Luhn 校验：从右数第 2、4、6… 位（0 基奇数索引）翻倍、超 9 减 9，总和整除 10。

## distinct_digits

- 数字串里出现过的不同数字个数（位掩码）。
