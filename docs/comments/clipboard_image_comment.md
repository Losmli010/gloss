## ClipboardImageReader（剪贴板图片取材读取器，2026-10-10，方案 §5.3；2026-10-10 评审修订）

- **为什么直读 NSPasteboard 的 flavor 数据而不是 arboard 的 `get_image`**
  （评审 HIGH 修订，推翻初版）：
  1. arboard 3.6.1 的 macOS 读图只请求 `public.tiff` 一种 flavor，PNG-only
     剪贴板（浏览器/文件复制常写 public.png）取材必失败且报
     `ContentNotAvailable`——若按竞态静默丢弃，用户“复制了图却毫无反应”
     且日志伪装成竞态，不可排查。方案 §5.3“arboard get_image() 得
     RGBA+尺寸”的前提（读图支持 TIFF/PNG）经源码核实不成立。
  2. arboard 的读图对解码无任何尺寸/字节设界——`get_image` 内部先整图
     解码再返回，像素面积上限只能判在分配之后，pastebomb 的最大一次内存
     分配（RGBA 位图，尺寸来自剪贴板内声明值）不受 `MAX_PIXELS` 约束。
  3. 直读 flavor（`dataForType:`，TIFF 先 PNG 后）让“哨兵认什么、取材读
     什么”在同一处对齐（两份候选表共用 `NSPasteboardTypeTIFF/PNG`），
     设界可以逐级前置（见下）。读内容触发 macOS 15+“允许粘贴”授权的
     时点不变（`dataForType:` 同样是内容读取）。
- **为什么竞态判定同时认两路（changeCount 不匹配 / 无可读图像 flavor）**：
  ①与②之间剪贴板被覆盖有两种可观察形态——被换成别的内容（changeCount
  前进）或被清空/换成非图像内容（`dataForType:` 对两种 flavor 都返回
  nil）。两路都落 `Ok(None)` 静默丢弃，与划词 `SelectionEmpty` 误滑同型
  处置：误触发不该弹失败卡打扰用户，留 debug 痕即可。只有“哨兵记录在、
  内容确实是可读图像、解码/编码环节真故障”才 `Err` 上抛 `TaskFailed`。
- **为什么 `Ok(None)` 表竞态而不是自定义错误变体**：竞态不是故障——下游
  不该有“失败”可观察（不弹卡、不占失败文案），但也不能混入 `Ok(Some)`
  的成功路径。`Result<Option<_>, _>` 三态恰好一一对应成功/静默/失败。
- **为什么硬失败映专用变体 `ImageUnavailable`**（2026-10-10 整体验收
  修订，推翻初版复用 `SelectionUnavailable` 的决策）：初版已知代价（失败
  卡文案“未能读取选中文本…”对图片任务措辞偏移、指引“重新选中”不可照
  做）在验收评审中被证实为可观察故障（LOW），故单开变体：失败指引落
  “重新复制”，i18n 双语各一键。变体族语义不变——粘贴板读不出（无可读
  flavor、授权被拒、板不可观察）与解不了码（头不可读、解码失败、缓冲与
  声明尺寸不符）同属“这张图取材失败”，与 `ImageTooLarge`（可照做：
  换张小图）分开建档。

## decode_to_png 的三级设界（评审 HIGH 修订）

- **为什么设界逐级前置（flavor 字节 → 头尺寸 → 整图解码）**：过去式炸弹
  （tiny_tiff/小 PNG 声明巨大尺寸）的危害在“按声明值分配”，声明值在头
  里。flavor 字节上限（64MiB）卡住编码数据本体；`into_dimensions()` 只读
  头拿声明尺寸，像素面积上限（4096²）在**任何大分配发生之前**拒绝超限；
  两关都过了才整图解码——合法满尺寸图像的解码峰值约 1.5–2 倍位图（解码
  中间缓冲 + RGBA 转换，约 100MB 量级），pastebomb 则是零大分配拒绝。
  产物侧仍有 PNG 字节上限（20MiB）。
- **为什么上限是这些数值**：flavor 64MiB——恰好 4096² 的未压缩 TIFF
  （RGB8）约 43MB，给满尺寸合法图像留量；面积 4096²（16MP）——4K 屏截图
  （8.3MP）在内，RGBA 位图恰达 64MB，超出即视为攻击性输入；PNG 20MiB——
  主流 LLM API 图像上传的常见门槛量级。都是源码常量（改数值同步 bdd.md），
  报错不截断——截断产物是静默数据损失。
- **为什么用 `ImageReader::with_format` 显式指定格式而不是 `with_guessed_format`**：
  读的是哪个 flavor（TIFF/PNG）已经确定，猜格式多一次内容嗅探且对截断
  输入可能猜错格式、把“截断”误报成“不支持的格式”。
- **为什么解码失败按读取失败（`ImageUnavailable`）而不是 ImageTooLarge**：
  头声明了合法尺寸但数据残缺，说明来源损坏（读到的不是一张完整图），不是
  “图太大”——错误类别要给用户正确的心智。头解析失败同理（哨兵已见图像
  flavor，读到却解不开，属取材失败）。

## read / read_with（两条静默丢弃路径的分岔，2026-10-10 整体验收修订）

- **为什么交付不出（changeCount 未变、板声明图像却读不出数据）单列 warn
  分支**：macOS 15+ 拒绝“允许粘贴”授权时 `dataForType:` 返回 nil，与
  “板上已无图像”同形。初版与竞态共用 `Ok(None)` 且留痕在调用方（文案
  误称“剪贴板已变化”，误导排查；debug 级在默认 info 过滤下零痕迹）。
  修订后分岔收进读取器：竞态（观察比对不过）debug、且**不读内容**（比对
  先于 flavor——内容读取才触发粘贴授权）；交付不出 warn，措辞点名授权
  可能被拒——`docs/tests/bdd.md` 的 L4 步骤（`just logs --level warn`
  有痕迹）按此口径成立。
- **为什么授权拒绝落静默丢弃而不是失败卡**：设计 §9 对拒绝路径只要求
  “失败卡或静默+日志”二选一。用户刚明确拒绝授权，紧接弹一张失败卡是对
  拒绝行为的二次打扰；warn 留痕已满足可观察。若日后要改失败卡，落点是
  这里加一个错误分支，读取器签名不变。
- **为什么系统读数走注入（`read_with`）**：竞态/无数据/不可观察三个分岔
  的落点（丢弃 vs 上抛、先比后读的次序）是行为契约，注入后纯逻辑单测可
  锁定（与哨兵源 `poll_at` 同型）；生产 `read` 只是把真实粘贴板读数喂进
  同一条路径，flavor 数据仍是零拷贝切片直通解码。

## encode_png（RGBA → PNG）

- **为什么快速压缩档（`CompressionType::Fast` + `FilterType::NoFilter`）**：
  编码在事件线程上同步执行，时长直接挂在“复制 → 弹卡”链路上；PNG 压缩
  的收益端在磁盘/网络，而这里的产物只活一跳——出网请求体（base64 后即弃）
  与内存会话。Fast+NoFilter 对照片类内容比默认档省一半以上编码时长，
  体积多出约 10–30%，换取弹卡延迟，划算。若将来缓存把 PNG 落盘（现行方案
  不落盘），再按落盘口径换档。
- **为什么 RGBA 缓冲与尺寸不符按读取失败而不是 ImageTooLarge**：不符说明
  来源数据损坏，是“读到的不是一张完整图”，不是“图太大”——错误类别要
  给用户正确的心智（重试大概率同样失败 vs 换张小图）。校验在前，
  `write_image` 的内部校验是第二道闸。
- **为什么不先经 `RgbaImage::from_raw` 而直接 `write_image(rgba, …)`**：
  from_raw 需要拿走 `Vec<u8>` 所有权，必然整块拷贝一次 RGBA；`ImageEncoder::
  write_image` 接受裸切片，零额外拷贝（大缓冲区不冗余克隆条目）。

## 符号契约（自代码注释迁入）

- `MAX_FLAVOR_BYTES`：flavor 字节上限：恰好 4096² 的未压缩 TIFF（RGB8）约 48MB，给满尺寸的合法图像留量；超限在头解析之前整体拒绝。
- `MAX_PIXELS`：像素面积上限：4096×4096 ≈ 16MP（4K 截图 8.3MP 在内）；面积在上限处的 RGBA 位图即 64MB，超出即视为 pastebomb。
- `MAX_PNG_BYTES`：PNG 字节上限：取材产物进 `TaskInput`、缓存会话与出网请求体，超限整体报错。
- `MAX_PRODUCT_SIDE`：产物最长边上限：取材产物经 base64 出网并入缓存会话，超过即按比例缩到上限内——视觉模型内部本就会把输入压到 ~1MP 一档，上限外的像素只有编码与传输成本；1536 长边覆盖图表与截图文字的判读质量，同时把解码后的 GPU 纹理与 base64 请求体的量级压到 ~9MB 档。上限以内的产物原样编码（不放大、不重采样）。
- `flavor_within_budget` / `pixels_within_budget` / `png_within_budget`：各预算是否在限内（纯逻辑，单测覆盖边界）。
- `downscaled_dims`：超限产物按比例缩到最长边上限内的目标尺寸（纯逻辑，单测覆盖）：上限以内返回 `None`（原样编码）；缩放按比例四舍五入、至少保留 1 像素。
- `decode_to_png`：图像 flavor 编码数据 → 解码 RGBA → 超长边降采样 → PNG（快速压缩档：编码在事件线程上执行，时长直接挂在触发到弹卡的链路上）。设界依次执行：flavor 字节上限在头解析之前，像素面积上限以仅读头的尺寸判定、先于整图解码，超 `MAX_PRODUCT_SIDE` 的产物按比例降采样，PNG 字节上限判在编码产物上。超限整体报 `ImageTooLarge`（不截断）；头不可读、解码失败、缓冲与尺寸不符都按读取失败处理。解码器构造两次是像素预算闸门的代价：先只读头取尺寸，超限的图不进整份解码（解压炸弹不该先吃掉内存再被拒），通过后才整份解码。
- `header_dimensions`：只读头取尺寸：超限的图在整份解码之前就被像素预算拒掉（解压炸弹不该先吃掉内存再被拒）；头不可读按读取失败处理。
- `decode_rgba`：整份解码为 RGBA8：已是 RGBA8 的图 `into_rgba8` 原地取出，不再整份复制。
- `downscale_to_budget`：超长边的产物按比例降采样到上限内，预算内原样归还。
- `encode_png`：RGBA 位图 → PNG。缓冲与声明尺寸不符按读取失败处理（校验在前，`write_image` 的内部校验兜底）。
- `ClipboardImageReader`：剪贴板图片读取器：通道②的取材实现（事件线程上顺序调用）。
  - `observer` 字段：① 观察记录的句柄：取材时比对现值判定①②之间的覆盖竞态。
  - `new`：句柄来自同一次装配的 `ClipboardWatchSource::observer`。
  - `read`：读剪贴板图片为 PNG 字节：`Ok(None)` = 静默丢弃（竞态或交付不出，读取器内已按分支留痕）；`Err` = 取材失败（调用方上抛 `TaskFailed`）。
  - `read_with`：一轮读取（系统读数注入，纯逻辑单测覆盖竞态与无数据的分岔——与哨兵源的 `poll_at` 同型）：板不可观察：读取失败上抛；changeCount 与①观察记录不一致：①②之间被覆盖，竞态静默丢弃，不读内容（比对先于 flavor——内容读取才触发系统粘贴授权）；板仍声明图像却交付不出数据：粘贴授权被拒走这条，warn 留痕后静默丢弃；可读：解码为 PNG。

## 产物最长边 2048 降采样（2026-10-16）

- 视觉模型内部会把输入压到 ~1–1.5MP，上限外像素只有编码与传输成本；
  base64 出网体积约缩 4×，图片任务的传输段 TTFT 与缓存会话同步受益。
  像素面积上限（4096²，pastebomb 闸门）与 PNG 字节上限不变——降采样只
  作用于已放行的产物。
