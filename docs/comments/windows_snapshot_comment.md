## snapshot_decision（2026-11-06，Windows 移植 P2①；2026-11-10 随图片板兜底修复更新边界）

- 快照的保全边界（与系统（macOS）同构、按系统（Windows）裁剪）：可读文本
  原样保全；板上无文本且格式计数为零＝确认的空板，按空板保全（恢复轮清
  板）；板上无文本但有格式（图片等非文本内容）按图像风格尽力保全——便
  携式网络图形（PNG）注册格式、版本 5 位图（CF_DIBV5）与位图（CF_DIB）
  按在板逐个捕获原始字节，超限或读不出的风格单独跳过（对应系统
  （macOS）的“读不出数据的风格单独跳过”），一个都保不住才整体放弃、不
  注入（对应系统（macOS）“条目的风格全部读不出即整体放弃”：注入后原
  内容无法如实写回，恢复轮会清空剪贴板）；板状态读不出同样放弃。
- 边界沿革：原边界“板上无文本但有格式即整体放弃”，快照只保全文本；代价
  是截图（进剪贴板的图片）注疏之后剪贴板兜底整批失效——划词探测收
  `SelectionUnavailable` 按误滑静默吞掉，用户感知为“截图注疏后划词不弹
  窗”。系统（macOS）侧无此问题（全风格保全），属移植缺口而非设计意图，
  故收口为图像风格原字节保全（写回字节即捕获字节，不经解码重编码；字节
  上限内的捕获在事件线程短暂驻留）。此项即移植评审遗留条目“多风格保全
  随图片取材阶段评估”的落地。
- 决策函数纯化（文本读取结果、格式清单查询、图像风格捕获三个入参）：单
  测以替身驱动全矩阵，不碰真板。
- 已知裁剪差异（登记后续收口意向）：文本与图像混合板仍走文本快照，恢复
  后图像丢失——与系统（macOS）全风格保全的差异继续存在，收口意向是文本
  可读时仍附带捕获图像风格（文本、图像两路保全并存）。

## SNAPSHOT_IMAGE_MAX_BYTES

- 图像风格捕获的单格式字节上限（64 MiB）：4K 屏位图（约 33 MB）与 5K 屏
  位图（约 59 MB）在内；超限风格单独跳过，全跳过回到整体放弃——巨板的
  忠实保全不值得在事件线程驻留百兆级缓冲，放弃轮不注入、板上原样。

## PendingRestore

- 恢复收尾：`restore_now`（恢复并返回写盘数）与 `skip_restore`（明示不恢
  复）；Drop 时未明示即恢复——调用方崩溃路径的兜底（与系统（macOS）同形）。
  恢复失败经统一出口记错误（环节、写盘数），不恐慌不上抛。
