# clipboard 决策记录（系统剪贴板文本写入的共享实现）

## `SystemClipboardWriter`（2026-10-27 建档于系统（macOS）剪贴板模块，2026-11-20 随整体终审意见上移共享层单源）

- **为什么走跨平台兜底库（arboard）**：其系统（macOS）面与系统（Windows）
  面都是各自剪贴板接口的文本格式封装，且模拟复制兜底的恢复序列已用同一
  库写回，写入口径一致；不手写不安全全局内存分配去换一个等价实现（质量
  条目“整段不安全设计优先换用安全封装”）。两侧实现逐字同一份（整体终审
  复测的平台镜像余量之一），故收进平台中立共享层，平台目录不再各持镜像。
- **为什么返回 `Result<(), String>` 而不是 panic/日志内部消化**：写剪贴板
  可能失败（板被占用等环境态），调用方（壳层，完成态卡“复制注疏”的平台
  触点）按失败记 warn 降级——浮层不弹错，复制是顺手功能不是任务出口。
- **为什么图像取材不走这里**：兜底库读图无尺寸设界且不认位图（DIB）家
  族，取材面留在各平台剪贴板模块另走系统接口（系统（macOS）读标记图像
  格式（TIFF）/便携式网络图形（PNG），系统（Windows）经外部函数接口
  （FFI）读 PNG/版本 5 位图（CF_DIBV5）/位图（CF_DIB）），理由见各平台
  剪贴板模块记录。
- **写板与取材通路的互斥**：与取材侧分属两个方向——取材读板、这条写板；
  兜底取材“只读不写”的红线不受影响：写板只发生在用户显式点击复制的会话
  内，且写入的是注疏产物（非用户原文）。写板推进板代数（系统（macOS）
  变更计数／系统（Windows）序列号）会被哨兵观察到一次板变更，但纯文本写
  不含图像风格，图像存在性判定不命中，哨兵不会为它触发取材——两条通路
  在类型判定处天然互斥。
