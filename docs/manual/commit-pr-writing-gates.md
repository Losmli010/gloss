# 提交与拉取请求书写门禁

提交信息与拉取请求（PR）标题、正文、评审结果与行内评论都有自动判罚的书写门禁（钩子工作流 `.github/workflows/hooks.yml`），生效分两级——**闸门**：作业列入 `main` 分支保护的必需检查，红灯挡合并直至修复；**红牌**：作业运行且红灯但不阻断合并，靠人看到后修复。不要带着红灯请求合并。

必需检查名单只有托管平台一份事实源——`main` 分支保护的必需状态检查清单（托管平台设置页的分支保护配置），本文不复抄——抄进文档就会漂移。

- **评审结果门禁**：评审提交或编辑即判——正文为空或纯空白判 `REVIEW-EMPTY`，缺评审模板骨架小节、缺声明或书写违规逐条判罚；判定挂在头提交（head SHA）上，作闸门。
- **内容快照锁定**：第一版标题加正文的摘要（SHA-256）以提交状态（commit status）挂在头提交，上下文名 `Content snapshot`，开启、同步与重开事件幂等重写；编辑事件比对当前摘要与快照，被改写即判 `PR-SNAPSHOT`，修复两种——恢复第一版内容，或在正文首行放 `snapshot:allow` 加缘由（豁免在场跳过判罚并以当前版重写基线）；机器人编辑按操作者排除，作闸门。
- **行内评论检查**：评论正文过书写规则，只做红牌，不拦合并。

生效边界：各检查都挂在拉取请求（PR）头提交（head SHA）上，合并完成后的编辑触发的重跑只能红牌——红灯落在已合并提交上，撤不回已合并提交，靠人看到后处置。

智能体开拉取请求（PR）走创建前预检：起草标题与正文两个文件，`just pr-lint-draft <title-file> <body-file>` 对草稿跑与持续集成（CI）同款判罚，绿灯后 `gh pr create`，开出后 `just pr-lint` 复检线上全文。本地拦截是软闸——版本库钩子覆盖不到创建动作，必需检查才是硬闸兜底。高频判罚点：

- **提交头限长**：提交信息首行（压缩合并时即拉取请求（PR）标题）按字节计上限 81，中文每字三字节，长标题先算字节；压缩合并产物还要追加编号后缀 `(#NNN)`，标题校验含合并模拟。
- **正文模板**：正文必须含模板全部必需小节（测试、安全与隐私、兼容性、文档同步、回滚），标题层级照模板抄。
- **书写规则**：正文不用直角引号（「」『』）等违禁标点，专有名词放全角括号注记；避免无谓的英中混排。

失败解读：判罚输出带规则标识（如 `PR-SECTION` 缺模板必需小节、`PR-PROSE` 书写违规）与违规位置，照标识修复后复跑 `just pr-lint-draft` 或 `just pr-lint` 确认。标题与正文在创建前修改零成本，创建后的编辑触发内容快照锁定判罚——第一版尽量一次写对。
