# 书写门禁

提交信息、拉取请求（PR）标题与正文、评审结果与行内评论都有自动判罚的书写门禁（钩子工作流 `.github/workflows/hooks.yml`），判罚输出带规则标识与修复指引，照标识修复后复跑同款入口确认。生效分两级——**闸门**：作业列入 `main` 分支保护的必需检查，红灯挡合并直至修复；**红牌**：作业运行且红灯但不阻断合并，靠人看到后修复。必需检查名单只有托管平台一份事实源——`main` 分支保护的必需状态检查清单（托管平台设置页的分支保护配置），本文不复抄——抄进文档就会漂移。

生效边界：各检查都挂在拉取请求（PR）头提交（head SHA）上，合并完成后的编辑触发的重跑只能红牌——红灯落在已合并提交上，撤不回已合并提交，靠人看到后处置。

三场景共用的书写规则：不用直角引号（「」『』）等违禁标点，专有名词放全角括号注记；避免无谓的英中混排。

## 提交信息

- **判罚入口**：提交时 `commit-msg` 钩子与持续集成（CI）的提交信息检查同一脚本（`scripts/hooks/check_commit_msg.py`），提交头形态、类型清单与正文书写规则以脚本为准；本地单条校验把提交信息写进文件后跑 `just lint-commit <file>`。
- **提交头限长**：首行（压缩合并时即拉取请求（PR）标题）按字节计上限 81，中文每字三字节，长标题先算字节；压缩合并产物还要追加编号后缀 `(#NNN)`，拉取请求（PR）标题的校验含合并模拟。
- **失败解读**：违规输出带规则标识（如超长 `COMMIT-LENGTH`、书写违规 `COMMIT-PROSE`）与违规位置，照标识修复后重新提交。提交信息判罚发生在提交落地之前；改写提交（amend）只该用在尚未推送的头提交上——头提交已推送时改写会造成历史分叉，一律追加新提交修正。

## 拉取请求（PR）内容

- **判罚入口**：钩子工作流的正文内容检查（PR content check）与本地预检同一脚本（`scripts/hooks/check_pr_prose.py`），标题与正文一并判罚，作闸门。
- **模板**：正文必需小节与标题层级以 `.github/pull_request_template.md` 为准，缺必需小节判 `PR-SECTION`，书写违规判 `PR-PROSE`；标题过压缩合并模拟（字节上限与编号后缀同提交信息），失败判 `PR-TITLE-SIM`。
- **创建前预检**：起草标题与正文两个文件，`just pr-lint-draft <title-file> <body-file>` 对草稿跑与持续集成（CI）同款判罚，绿灯后 `gh pr create`，开出后 `just pr-lint` 复检线上全文。本地拦截是软闸——版本库钩子覆盖不到创建动作，必需检查才是硬闸兜底。
- **内容快照锁定**：第一版标题加正文的摘要（SHA-256）以提交状态（commit status）挂在头提交，上下文名 `Content snapshot`；编辑事件比对当前摘要与快照，被改写即判 `PR-SNAPSHOT`，修复两种——恢复第一版内容，或在正文首行放 `snapshot:allow` 加缘由（豁免在场跳过判罚并以当前版重写基线）；机器人编辑按操作者排除。标题与正文创建前修改零成本，创建后编辑要过快照判罚——第一版尽量一次写对。

## 评审内容

- **评审结果**：评审提交或编辑即判，作闸门——正文为空或纯空白判 `REVIEW-EMPTY`；模板骨架小节、声明与书写规则以 `.github/review_result_template.md` 为准，缺项或违规逐条判罚。
- **行内评论**：评论正文过书写规则，只做红牌，不拦合并。
